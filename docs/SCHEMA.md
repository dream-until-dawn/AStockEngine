# 数据 Schema 定义

> **状态：待评审**（v0.1 开工前需定稿）
> 最后更新：2026-08-28
> 依据：[ROADMAP.md](ROADMAP.md) 的「数据存储设计」章节与 [v0.0 探针结论](probe/REPORT-v0.0.md)

本文档是 **Python ETL 与 Go 引擎唯一的契约**。两侧实现必须严格一致，
任何字段变更都是双边改动，因此本文档定稿后的修改需同步升级 `schema_version`。

## 0. 通用约定

### 0.1 类型选择原则

沿用 ROADMAP 的**保守子集原则**：只使用各语言 Parquet 实现都成熟支持的类型。

- 整数一律用**有符号**类型（`INT8` / `INT32` / `INT64`）。
  无符号类型在部分实现中支持不一致，而 `INT32` 的 21 亿容量远超本项目需求。
- 不使用 `DECIMAL` 逻辑类型 —— 跨语言支持参差，改用**定点整数 + scale**。
- 不使用 `DATE` / `TIMESTAMP` 逻辑类型 —— 时区语义在各实现间存在分歧，
  改用显式的 `INT32 (YYYYMMDD)` 与 `INT64 (UTC 毫秒)`。
- 布尔语义用 `INT8`（0/1）而非 `BOOLEAN`，便于与多值枚举统一处理。

### 0.2 定点整数约定

| 概念 | 表示 | scale 来源 |
|---|---|---|
| 价格 | `INT64` | `instruments.price_scale`（A 股 = 1000；加密 = 1e8） |
| 数量 | `INT64` | `instruments.qty_scale`（A 股 = 1，即 1 股/份；加密 = 1e8，单位为**张**） |
| 金额 | `INT64` | 固定为计价币种最小单位（A 股 = 分；加密 = 1e-2 USDT） |
| 比率 | `INT32` | 固定 1e6（如换手率 0.256% 存为 `256000`） |

> 价格用定点整数**不是为了体积**（实测仅比 float64 省 6%），
> 而是为了约束 C5 可复现性：浮点累加顺序不同会导致结果不同，
> 并发海选下无法保证逐笔一致。详见 ROADMAP「关键类型决策」。

**scale 是逐标的的，不是逐市场的。** 这一点在只有 A 股时看不出来，
加了加密货币才成为必需 —— 见 0.6。

### 0.3 时间约定

| 字段 | 类型 | 定义 |
|---|---|---|
| `ts_open` | `INT64` | **UTC 毫秒**，bar 的**起始时刻**。A 股日线 = 09:30 CST = 01:30 UTC |
| `ts_close` | `INT64` | **UTC 毫秒**，bar 的**结束时刻**。A 股日线 = 15:00 CST = 07:00 UTC |
| `trading_day` | `INT32` | `YYYYMMDD`，业务语义的交易日 |
| 其余日期字段 | `INT32` | `YYYYMMDD` |

#### 为什么两端都存

**单一的 `ts` 字段名本身就是缺陷**：它不表明指向哪一端，
而不同数据源的惯例恰好相反 ——

| 来源 | 惯例 |
|---|---|
| Binance kline | `[0]` 为 **Open time**，`[6]` 为 Close time |
| OKX candlesticks | `ts` 为 K 线**开始时间** |
| 传统日线数据 | 通常只给交易日期，无时刻语义 |

若沿用外部惯例只存起始时刻，引擎必须自行推导结束时刻；
而 A 股日线的「时长」并非固定时段（09:30 开、15:00 收，中间有午休），
推导依赖交易时段知识 —— **这正是产生未来函数 off-by-one 的典型位置**，
直接违背首要约束 C1。

因此两端都存，且**用名称消除歧义**。实测代价 **+1.22%**（全市场 +4.3 MB），
与 `trading_day` 的刻意冗余同理。

#### 各市场的日线时刻

| 市场 | `ts_open` | `ts_close` | 切日口径 |
|---|---|---|---|
| `ashare` | 当日 09:30 CST | 当日 15:00 CST | 交易日历 |
| `crypto` | 当日 00:00 **CST** | **次日** 00:00 CST | UTC+8 自然日，24×7 |

加密货币按 **UTC+8 切日**（已定，2026-08-29）。理由有两条：
一是 OKX 的 `bar=1D` 本来就是这个口径（`1Dutc` 才是 UTC 0 点），
按 UTC 切要自己重新聚合，凭空引入一层可能出错的转换；
二是与 A 股同处一条时间轴时，日期对得上 —— 「2024-03-14 的 BTC」
与「2024-03-14 的 A 股」说的是同一天。

24×7 市场没有午休，一根 bar 结束就是下一根开始，
故 `ts_close − ts_open` 恒为 86,400,000 ms。
**这不代表可以由 `ts_open` 推出 `ts_close`** —— 0.3 的两端都存规则依旧，
理由见上文（推导是 off-by-one 的高发位置）。

#### 引擎使用规则

- **时间游标一律使用 `ts_close`** —— 它才是「该 bar 信息可得」的时刻
- `ts_open` 仅用于与外部数据源对齐、图表展示，以及远期 24×7 市场的自然索引
- **策略侧不得访问 `ts_open`**，避免误用为决策时点

> **已定**：A 股开盘价实际产生于 09:25 的集合竞价，但**本项目不建模集合竞价**
> （见 ROADMAP C8「明确不建模的机制」），故 `ts_open` 取 09:30（连续竞价开始）。
> 该约定在仅日线的范围下不产生歧义 —— 日线数据本就不含竞价阶段的委托明细。

### 0.4 枚举定义

枚举值的含义以本文档为准，Python 与 Go 两侧各自实现为编译期常量。
**0 一律保留为「未知/无效」**，便于识别未初始化数据。

```
market      1=ashare  5=crypto           远期：2=us  3=hk  4=futures
exchange    1=SSE(上交所)  2=SZSE(深交所)  3=BSE(北交所)   10=OKX
type        1=stock(个股)  2=etf                        10=swap(永续合约)
board       1=主板  2=创业板  3=科创板  4=北交所           加密货币恒为 0
quote_ccy   1=CNY                                      10=USDT
status      1=在市  2=已退市
```

**分段规则**：`exchange` / `type` / `quote_ccy` 的 **10 起留给非 A 股**
（非 A 股交易所、衍生品、非法币）。A 股的取值因此还能继续往下加，
不必为了插一个新交易所去动已有数据。`market` 的 2–4 已经预留给
美股/港股/期货，加密取 5。

> `board` 对加密货币记 **0（unknown）而不是 1（主板）**。
> `tracked_board` 在引擎里决定涨跌停幅度 —— 塞一个假板块进去，
> 引擎会安静地给 BTC 套上 ±10% 的涨跌停，而且不报任何错。

### 0.5 排序保证

`bar` 表的每个文件内部必须按 **`(instrument_id, ts_close)` 严格升序**。

这不是可选优化：`DELTA_BINARY_PACKED` 编码的压缩效果依赖于此，
引擎的顺序扫描也假定此前提。ETL 必须在写出前排序，质检需校验。

### 0.6 int64 的精度边界

加密货币的报价常见 8～18 位小数，「用 int64 存得下吗」不是一个可以拍脑袋的问题。
算一遍：

```
int64 上限        9,223,372,036,854,775,807     ≈ 9.22e18，共 19 位十进制
定点表示的可表示上限 = 上限 ÷ scale
```

| scale | 小数位 | 可表示的最大值 |
|---|---|---|
| 1e18 | 18 | **9.22** ← 连 10 都存不下 |
| 1e12 | 12 | 9.22e6 |
| 1e8 | 8 | **9.22e10** |
| 1e3 | 3 | 9.22e15 |

**结论：「18 位精度」与 int64 不可兼得。** 18 位小数把可表示上限压到 9.22，
BTC 的价格直接溢出。以太坊生态的 18 位小数（wei）用的是 256 位整数，
不是 int64 —— 换 int64 就必须换一个位数。

真正需要的不是「18 位小数」而是**足够的有效数字 + 逐标的的小数点位置**，
这正是 `price_scale` / `qty_scale` 存在的理由。取 `1e8`（satoshi 级，
也是加密圈的惯例）后的实测余量：

| 标的 | 最大定点值 | 离 int64 上限的余量 |
|---|---|---|
| BTC 收盘价 | 1.25e13 | 73.8 万倍 |
| 日成交量（张） | 1.25e17 | 74 倍 |
| 日成交额（分） | 9.15e12 | 100.8 万倍 |

（由 `etl/build_crypto.py` 每次运行时实测打印，不是估算。）

**数量的 74 倍是三者里最紧的一项。** 将来接成交量更大的小币种时，
先看 `build_crypto.py` 打印的实测余量再定 scale，别照抄 1e8。

#### 乘积会溢出 —— 这条必须写在引擎里

单个值余量充足，**两个定点数相乘不是**：

```
price_fp × qty_fp = 1.25e13 × 1.25e17 = 1.56e30   ≫ 9.22e18
```

算名义额、保证金、手续费时若直接 `price * qty` 再除 scale，
在加密标的上会**静默回绕成负数**。必须先约分再乘（mulDiv 拆分），
或者用 `math/bits.Mul64` 做 128 位中间结果。

A 股上这个问题被规模掩盖了（1e3 × 1e0 = 1e3 的 scale 乘积），
所以它是一个**加了加密货币才会暴露的既有缺陷**，
而不是加密货币特有的麻烦。

## 1. `bar` —— 行情时序

**路径**：`data/bar/market={market}/freq={freq}/year={YYYY}/part-*.parquet`
**主键**：`(instrument_id, ts_close)`
**规模**：A 股日线全量约 2000 万行 / 约 360 MB；加密（BTC/ETH 永续）4,930 行 / 236 KB
**编码**：定点整数 + `DELTA_BINARY_PACKED` + zstd(level 3)

### 1.1 核心列 —— 全市场严格统一

引擎核心循环只读这 10 列。**其名称与语义不可变更**，新增市场必须能填满它们。

| 字段 | Parquet | Go | 可空 | 说明 |
|---|---|---|---|---|
| `instrument_id` | INT32 | `int32` | 否 | 引擎内部 ID，见 `instruments` |
| `ts_open` | INT64 | `int64` | 否 | UTC 毫秒，bar 起始时刻。**策略侧不得使用** |
| `ts_close` | INT64 | `int64` | 否 | UTC 毫秒，bar 结束时刻。**时间游标用此列** |
| `trading_day` | INT32 | `int32` | 否 | YYYYMMDD |
| `open` | INT64 | `int64` | 否 | 定点价格 |
| `high` | INT64 | `int64` | 否 | 定点价格 |
| `low` | INT64 | `int64` | 否 | 定点价格 |
| `close` | INT64 | `int64` | 否 | 定点价格 |
| `volume` | INT64 | `int64` | 否 | 定点数量 |
| `amount` | INT64 | `int64` | 否 | 成交额，单位为分 |

> **均为不可空**。停牌日的处理不是「置空」而是写入零成交行并由
> `tradestatus` 标记 —— 见 1.3。

### 1.2 A 股扩展列

直接附于同表。Go 侧用只含核心列的 `CoreBar` struct 亦可读取
（已由 `engine/cmd/subsetread` 实测验证）。

| 字段 | Parquet | Go | 可空 | 说明 |
|---|---|---|---|---|
| `preclose` | INT64 | `int64` | 否 | **除权调整后的前收盘价**，涨跌停基准（C8.1） |
| `turn` | INT32 | `int32` | 否 | 换手率，百分数 ×1e6 |
| `tradestatus` | INT8 | `int8` | 否 | 1=正常交易 0=停牌 |
| `is_st` | INT8 | `int8` | 否 | 1=ST 0=非 ST。**影响涨跌停幅度**（ST 为 5%） |

加密货币的 bar **复用同样四列**（取值见 1.5），不另立分支 ——
核心 10 列 + A 股扩展 4 列就是当前的全部 bar 结构。

远期其他市场的扩展列：`us` → `pre_market_volume`；
`futures` → `open_interest` / `settlement`。

### 1.3 停牌行的语义

> `tradestatus = 0` 的通用语义是「**该 bar 不可成交**」，停牌只是它在 A 股的成因。
> 加密货币的零成交日复用同一标记，见 1.5。

BaoStock 在停牌日**照常返回行**，因此 `bar` 表与交易日历对齐，
且天然具备 point-in-time 语义：

```
某日标的池 = SELECT DISTINCT instrument_id FROM bar WHERE trading_day = d
```

停牌行的取值（**v0.0 已实测确认**，保千里 84 个停牌日、乐视网 107 个停牌日）：

- `tradestatus = 0`
- `volume = 0`、`amount = 0`
- `open = high = low = close = preclose` = 停牌前最后收盘价
  （价格序列因此保持连续，指标计算不会出现空洞，无需 ETL 回填）

```
date        open   high   low   close  preclose  volume  amount  turn  tradestatus
2019-04-26  1.0400 1.0400 1.0400 1.0400  1.0400      0   0.0000  (空)      0
```

> ⚠️ **解析注意**：停牌行的 `turn` 是**空字符串**而非 `0`。
> ETL 必须以 `pd.to_numeric(errors="coerce").fillna(0)` 之类的方式容错，
> 直接 `float("")` 会抛异常。

### 1.4 ETF 的字段缺口

新浪 `fund_etf_hist_sina` **不提供 `preclose`**（仅少数标的带 `prevclose`），
也不提供 `turn` / `tradestatus` / `is_st`。ETF 行的处理约定：

| 字段 | ETF 取值 |
|---|---|
| `preclose` | 由 `corporate_action` 推算；无除权则取前一交易日 `close` |
| `turn` | 0（新浪不提供流通份额，无法计算） |
| `tradestatus` | 1（新浪无停牌标记，缺行即视为停牌/未上市） |
| `is_st` | 0（ETF 无 ST 概念） |

> ⚠️ 这是**已知的数据质量降级**，必须在质检报告中单独计数，
> 且 Web 端在回测 ETF 时应提示 `turn` 不可用。

### 1.5 加密货币的字段缺口

与 1.4 的 ETF 同理：**能填的填，填不了的记默认值并在这里写明白**，
不编数据。

| 字段 | 加密取值 | 为什么 |
|---|---|---|
| `preclose` | 前一根的 `close` | 没有除权，前收就是前收 |
| `volume` | **张数**，×1e8 | 见下 |
| `amount` | USDT 计价额（OKX `volCcyQuote`），单位 1e-2 | |
| `turn` | 0 | 永续合约没有流通股本，换手率无从谈起 |
| `tradestatus` | **零成交日记 0**，否则 1 | 见下 |
| `is_st` | 恒为 0 | 无此概念 |

**数量单位是「张」不是「币」**（已定，2026-08-29）。
1 张 BTC-USDT-SWAP = 0.01 BTC，1 张 ETH-USDT-SWAP = 0.1 ETH，
乘数存在 `instruments.attrs.ct_val`。选张而非币的理由：
张是交易所实际的下单单位，`lotSz` / `minSz` 都以张计 ——
存币数就要在下单时换回去，而那次换算会引入取整误差。

> **名义额 = 张数 × `ct_val` × 价格。** 少了 `ct_val` 这一项，
> `volume` 这一列没有意义 —— 引擎必须读 `attrs`。

#### 零成交日复用 `tradestatus = 0`

加密货币不停牌，但**确实存在整天没有成交的 bar** ——
OKX 早期数据里 BTC 有 7 天、ETH 有 8 天（全部在 2019-12），
其 OHLC 是拿上一根的价格铺平的，与 1.3 描述的 A 股停牌行形态一模一样。

记成 `1` 的话，引擎会把它当成一个可以按 7,820 成交的正常交易日 ——
而那一天根本没有对手盘。**「没有流动性」与「正常交易」必须可区分**，
既有的 `tradestatus` 恰好就是表达这件事的字段，不必新造一个。

于是 1.3 的语义在这里从「停牌」推广为「**该 bar 不可成交**」，
停牌只是它在 A 股的一种成因。`Bar.Suspended()` 的调用方无需改动。

#### `funding_rate` 在 `funding` 表，不在 bar 里

永续合约每 8 小时结算一次资金费率（多空互付），**实测其影响超过
A 股一个年换手 24 倍的策略的全部摩擦**。详见第 6 节。

它没有塞进 bar 表：结算频率（8h）与 bar 频率（1d）不同，
塞进来就要先聚合，而聚合方式本身是个会影响结果的选择 ——
那个选择应当留在引擎里。

当前状态：**数据已采集（覆盖约 3.9%），引擎尚未计费**。
`instruments.attrs.funding_rate` 记 `"collected_not_charged"`。

## 2. `instruments` —— 标的静态属性

**路径**：`data/meta/instruments.parquet`（+ `instruments.csv` 镜像）
**主键**：`instrument_id`
**唯一约束**：`(market, symbol)`
**规模**：7202 行（A 股个股 5549 + ETF 1651 + 加密永续 2）

| 字段 | Parquet | Go | 可空 | 说明 |
|---|---|---|---|---|
| `instrument_id` | INT32 | `int32` | 否 | 主键，从 1 开始 |
| `market` | INT8 | `int8` | 否 | 枚举，见 0.4 |
| `symbol` | STRING | `string` | 否 | 市场内唯一。A 股为 6 位数字，**不含交易所前缀** |
| `exchange` | INT8 | `int8` | 否 | 枚举 |
| `name` | STRING | `string` | 否 | 当前/最终名称。**不做时变**，见下方说明 |
| `type` | INT8 | `int8` | 否 | 1=个股 2=ETF 10=永续合约 |
| `board` | INT8 | `int8` | 否 | 标的自身所属板块 |
| `tracked_board` | INT8 | `int8` | 否 | **决定涨跌停幅度**，Market 模块使用。见 2.5 |
| `price_scale` | INT32 | `int32` | 否 | A 股 = 1000；加密 = 1e8 |
| `qty_scale` | INT32 | `int32` | 否 | A 股 = 1（股/份）；加密 = 1e8（张） |
| `quote_ccy` | INT8 | `int8` | 否 | A 股 = 1 (CNY)；加密 = 10 (USDT) |
| `min_order_qty` | INT32 | `int32` | 否 | 最小申报数量 |
| `qty_step` | INT32 | `int32` | 否 | 申报数量递增单位 |
| `list_date` | INT32 | `int32` | 否 | 上市日 YYYYMMDD |
| `delist_date` | INT32 | `int32` | **是** | 退市日；在市为 null |
| `status` | INT8 | `int8` | 否 | 1=在市 2=已退市 |
| `attrs` | STRING | `string` | **是** | 市场特定属性，JSON |

### 2.1 `min_order_qty` / `qty_step` 取值

| 板块 | `min_order_qty` | `qty_step` |
|---|---|---|
| 主板 / 创业板（个股） | 100 | 100 |
| 科创板（个股） | 200 | 1 |
| ETF | 100 | 100 |
| 北交所 | 100 | 1 |
| 加密永续（BTC/ETH） | 1,000,000（= 0.01 张 ×1e8） | 1,000,000 |

> 北交所规则**已核实**：单笔申报不低于 100 股，以 **1 股**为单位递增
> （来源：广发基金、证券时报对《北交所交易规则》的解读）。
>
> 卖出零股（不足最小单位的余股）必须一次性全部卖出 —— 这是 Broker 的规则，
> 不在本表体现。

### 2.5 `tracked_board` 与 `board` 的区别

个股的两者相同。**ETF 不同**：ETF 的涨跌停由其**跟踪的指数**决定 ——
跟踪创业板 / 科创板指数者为 20%，其余为 10% —— 而 ETF 自身不属于任何板块，
`board` 对 ETF 统一记为主板。

判定由 `etl/infer_etf_board.py` 完成，**价格实证为主、名称为辅**：

- 价格证据：历史上 `|涨跌幅| > 10.5%` 的**次数** ≥ 2
- 名称关键词：科创 / 创业板 / 双创等（价格证据不足时的兜底）

用「次数」而非「最大值」，是为了打破一个循环依赖：要判断某个 19% 的涨幅
是否不可能，得先知道该 ETF 的涨跌停，而涨跌停正是待推断的对象。
次数则不循环 —— 真正 20% 限制的 ETF 会**多次**超限，
而一个未修正的折算事件只贡献**一次**。

> 该判定顺带成了复权缺口的探测器：「恰好一次超限且名称无关键词」
> 高度指向尚未修正的折算事件。当前检出 1 只（510100 于 2023-02-13），
> 已列入已知缺口。

### 2.2 关于 `name` 不做时变

严格说名称是时变的（`乐视网` → `*ST视退`），标准做法是
`(instrument_id, name, valid_from, valid_to)` 区间表。本项目**刻意不做**：

- 策略不消费名称，它只影响展示
- BaoStock 不提供历史名称，做区间表需引入新数据源

代价：回看 2019 年的回测报告时，显示的是标的**当前/最终**名称。

> **已确认**（2026-08-28 评审）：接受此代价。
> 若将来判定不可接受，再补 `instrument_name` 区间表，不影响其他表。

### 2.3 `attrs` JSON

A 股标的此列为 null。加密永续合约的实际取值（OKX 原样字段 + 两个自加项）：

```json
{
  "ct_val": "0.01", "ct_val_ccy": "BTC", "ct_mult": "1", "ct_type": "linear",
  "tick_sz": "0.1", "lot_sz": "0.01", "min_sz": "0.01",
  "settle_ccy": "USDT",
  "source": "okx",
  "funding_rate": "not_collected"
}
```

- `ct_val` **是必读项**，不是备注：名义额 = 张数 × `ct_val` × 价格（见 1.5）
- 数值一律**存为字符串**，与 OKX 返回保持一致 ——
  `0.01` 转成 float 再存回去会引入一次没必要的精度损失，
  而这个值是要参与金额计算的
- `funding_rate: "not_collected"` 是**显式的缺口标记**，见 1.5

远期市场：

```json
// futures
{"contract_multiplier": 300, "expiry_date": 20240315, "underlying": "IF"}
```

instruments 仅数万行，全量载入内存后解析 JSON 无性能顾虑，
换来的是**新增市场不改表结构**。

### 2.4 `instrument_id` 分配规则

**这条规则关系到增量更新的正确性，必须严格遵守：**

1. 按 `(market, symbol)` **首次出现**时分配，单调递增，从 1 开始
2. **永不复用**，即使标的退市
3. ETL 每次运行必须先读取已有 `instruments.parquet` 取得现有映射，
   仅为新标的分配新 ID
4. 若 `instruments.parquet` 丢失，则所有 ID 会重新分配，
   **既有的 `bar` 分区文件随之全部失效**，必须整体重建

> 因此 `instruments.parquet` 是整个数据集里最关键的单个文件。
> 质检需校验其单调性与唯一性；建议 ETL 每次运行前自动备份该文件。

## 3. `calendar` —— 交易日历

**路径**：`data/meta/calendar.parquet`（+ CSV 镜像）
**主键**：`(market, date)`
**规模**：约 9000 行/市场

| 字段 | Parquet | Go | 可空 | 说明 |
|---|---|---|---|---|
| `market` | INT8 | `int8` | 否 | 枚举 |
| `date` | INT32 | `int32` | 否 | YYYYMMDD |
| `is_trading_day` | INT8 | `int8` | 否 | 1=交易日 0=非交易日 |

日历包含非交易日（`is_trading_day = 0`），便于直接做日期区间运算，
无需另行判断周末与节假日。

**加密货币在本表中没有行。** 24×7 市场没有交易日历这回事，
写一份「每天都是交易日」的 9000 行进去只是把常量存成了数据。
代价是 `Calendar.TradingDaysPerYear(MarketCrypto, ...)` 数不出东西、
回退到兜底值 252 —— 而加密的正确值是 365，**错 45% 足以改变结论**。

**已解决**：年化系数改由 `trading.Market.AnnualDays()` 提供
（A 股走日历实测 242.54，24×7 市场直接返回 365），
不再由调用方写死 `MarketAShare` 去查日历。

## 4. `adj_factor` —— 复权因子

**路径**：`data/meta/adj_factor.parquet`（+ CSV 镜像）
**主键**：`(instrument_id, ex_date)`
**规模**：约 20 万行（每标的数十行）
**语义**：**事件式**，仅在除权日给出一行；**自 `ex_date` 当日起生效**（前向填充）

| 字段 | Parquet | Go | 可空 | 说明 |
|---|---|---|---|---|
| `instrument_id` | INT32 | `int32` | 否 | |
| `ex_date` | INT32 | `int32` | 否 | 除权除息日 YYYYMMDD |
| `hfq_factor` | INT64 | `int64` | 否 | 后复权因子，定点 **scale = 1e12** |
| `hfq_factor_raw` | STRING | `string` | 否 | 数据源原始字符串，保留 16 位精度用于审计 |

### 4.1 为什么存两份

数据源（新浪）返回的因子是 **16 位精度的字符串**，直接 `float()` 会丢精度。

- `hfq_factor`：定点 int64，scale 1e12，供引擎直接使用，**无需 Go 端引入 Decimal 库**
- `hfq_factor_raw`：原样保留字符串，用于审计与将来重算

精度核算：因子实际范围约 1~10000，`10000 × 1e12 = 1e16 < 9.2e18`（int64 上限），
不会溢出；scale 1e12 提供 13 位有效数字，而 v0.0 实测的还原相对误差为 4.19e-07
（受限于数据源后复权价的 2 位小数），13 位有效数字远超所需。

### 4.2 使用方式

```
后复权价(d) = 原始价(d) × hfq_factor(最近一个 ex_date <= d) / 1e12
```

无匹配记录时（标的上市至今无除权）因子取 `1e12`（即 1.0）。

> **前复权价禁止持久化**（C2）：它锚定在最后一个交易日，
> 每次新除权都会改写全部历史值，既不可复现，本身也是未来函数。

## 5. `corporate_action` —— 分红送配

**路径**：`data/meta/corporate_action.parquet`（+ CSV 镜像）
**主键**：`(instrument_id, ex_date)`
**用途**：Portfolio 模块据此将现金分红入账、送转股增加持仓（C2）

| 字段 | Parquet | Go | 可空 | 说明 |
|---|---|---|---|---|
| `instrument_id` | INT32 | `int32` | 否 | |
| `ex_date` | INT32 | `int32` | 否 | 除权除息日 |
| `record_date` | INT32 | `int32` | 是 | 股权登记日 |
| `pay_date` | INT32 | `int32` | 是 | 派息日。当前数据源不提供，恒为 null（见 5.3） |
| `cash_before_tax` | INT64 | `int64` | 否 | **每股**税前现金红利，定点 scale 1e6（元） |
| `stock_dividend` | INT64 | `int64` | 否 | **每股**送股数，定点 scale 1e6 |
| `stock_transfer` | INT64 | `int64` | 否 | **每股**转增股数，定点 scale 1e6 |
| `rights_ratio` | INT64 | `int64` | 否 | **每股**配股数，定点 scale 1e6 |
| `rights_price` | INT64 | `int64` | 否 | 配股价格，定点（见 `price_scale`） |

### 5.2 配股为何单列两个字段

配股同样导致除权，但 Portfolio 的处理与分红送转**完全不同**：
配股需要股东按 `rights_price` 掏钱认购 `rights_ratio` 份额，不认购则被稀释。
回测须显式选择「参与 / 不参与」，因此价格与比例两者都要存。

数据源的 `分红` 与 `配股` 是同一接口的不同 `indicator`，字段结构也不同，
须分别抓取。v0.1 首轮只取了 `分红`，导致 7889 个复权因子事件找不到对应记录
（如 600001 于 2000-05-29 的配股）。

### 5.3 不存税后金额

BaoStock 的 `dividCashPsAfterTax` 存在 `"27.7884或30.876"` 这类
**非数值字符串**（税率分档所致）。

红利税属于**规则**而非数据：税率随持股期限变化，应由 `Fee` / `Portfolio`
模块按 `configs/fee/*.json` 计算。因此本表**只存税前金额**。

> **已确认**（2026-08-28 评审）：税率计算归 Fee 模块。

## 6. `funding` —— 永续合约资金费率

**路径**：`data/meta/funding.parquet`（+ CSV 镜像）
**主键**：`(instrument_id, funding_time)`
**规模**：577 行（BTC 288 + ETH 289）

| 字段 | Parquet | Go | 可空 | 说明 |
|---|---|---|---|---|
| `instrument_id` | INT32 | `int32` | 否 | |
| `funding_time` | INT64 | `int64` | 否 | 结算时刻，**UTC 毫秒**，每 8 小时一条 |
| `trading_day` | INT32 | `int32` | 否 | 该时刻所属的 UTC+8 自然日，供按日 join |
| `rate` | INT64 | `int64` | 否 | 费率，scale **1e12**。**正 = 多头付空头** |
| `rate_raw` | STRING | `string` | 否 | 原始字符串，供将来重算 |

### 6.1 为什么它不能省

永续合约没有交割日，靠这笔多空互付把合约价钉在现货附近。**实测**
（OKX 公开端点，2026-05-25 ~ 08-29 共 289 次结算）：

| | 单次中位 | 多头付钱的比例 | 年化（做多方付出） |
|---|---|---|---|
| BTC-USDT-SWAP | +0.0042% | **82.4%** | **+4.4%** |
| ETH-USDT-SWAP | +0.0026% | 72.7% | +2.9% |

对照：`macd_cross` 在 A 股 6.6 年的**全部**摩擦（佣金+印花税+过户费+滑点）
是 20.45%，年化约 3.1%。

> **一个 BTC 多头的资金费率，比一个年换手 24 倍的 A 股策略的全部摩擦还贵。**
> 而且它是单向的 —— 82% 的时间多头在付钱。

### 6.2 为什么存 8h 原始粒度而不是聚合成日频

聚合方式本身会影响结果：按日求和？按持仓时段加权？持仓半天算不算？
这些选择必须留在引擎里，由持仓的实际起止时刻决定 ——
预先聚合等于替引擎做了一个它无从察觉的决定。

代价是表变大 3 倍。577 行的表，无所谓。

### 6.3 ⚠ 只有约 3 个月的历史

**OKX 的公开端点只保留约 3 个月**（实测 `after=2024-06-01` 返回 0 条）。
6.6 年的行情，费率覆盖 **3.9%**（BTC 95/2466 天、ETH 96/2464 天）。

这是数据源限制，不是 ETL 的问题。

**已定（2026-08-29）：统一忽视资金费率，但必须显式披露。**

不做「有数据的段算、没数据的段不算」—— 那比统一不计更糟，
它让同一次回测的两段用了不同的成本模型，而报告上看不出任何异常。

落地形态是 `Config.Disclosures()`：标的池里有永续合约时返回一条
「资金费率未计入」，**CLI 报告与 Web 端都必须显示**。
只存在于文档里的缺口，等于不存在。

### 6.4 引擎侧尚未计费

表建好了、数据拉了，但 `Ledger` 还不会在持仓期间扣这笔钱 —— 那要等
CryptoMarket。`instruments.attrs.funding_rate` 现在记
`"collected_not_charged"`，与之前的 `"not_collected"` 区分开。

在那之前，`Config.Disclosures()` 会在任何含永续合约的回测里
把这件事印在报告上（见 6.3）。

{
  "schema_version": "1.0.0",

#### 数据指纹跨市场耦合（已记录，v0.5 处理）

数据指纹哈希 `data/` 下**全部** parquet 的内容。于是加密数据一落盘，
所有 A 股跑批的**输入指纹全变了** —— 尽管结果一个字节没变
（v0.3.3 实测：三个基线输出指纹逐位一致）。

**这不是正确性问题。** C5 的保证是单向的：同输入指纹 ⇒ 同输出指纹。
输入变了只意味着「需要重新验证」，不意味着「结果错了」。

**是成本问题**，而且只在 v0.5 才会疼：海选把指纹存进 results 表后，
每加一个市场就让全部历史结果的指纹作废，无法判断哪些还能复用。

**倾向的改法**（v0.5 落地时再定）：bar 部分**按本次实际读取的文件集**
计算指纹（loader 本来就知道自己读了哪些文件），meta 保持整表哈希。
这样 A 股跑批不受加密数据影响，而 instruments 变了确实该重跑。

现在不动它 —— 改了没有收益，而每一次动指纹口径都会让此前记录的
指纹失效一次。

#### `is_st` 需要交叉校验

v0.0 抽样时发现：乐视网（sz.300104）2019-04-26 至 05-08 期间 `isST=0`，
而该标的当时可能已被实施退市风险警示。样本量不足以断言数据源有误，
但 `is_st` **直接决定涨跌停幅度**（ST 为 5%），标记错误会导致 Broker 误判。

由于不保留历史名称（2.2），无法用「名称含 ST 前缀」交叉核对。
改用**自洽校验**，列入 v0.1 质检项：

- `is_st = 1` 的交易日，其 `(close - preclose) / preclose` 不应超过 ±5%
- `is_st = 0` 的主板标的，不应超过 ±10%

（均需排除上市首日与除权日）越界即说明 `is_st` 或 `board` 标记有误。
