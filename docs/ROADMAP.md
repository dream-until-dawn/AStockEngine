# AStockEngine 版本路线图

> 本文档是项目的**活文档**，版本内容或优先级发生调整时同步更新。
> 最后更新：2026-08-30（v0.4 单步调试完成；此前 v0.3.1 回测结果视图、v0.3.2 模块化补强、v0.3.3 加密数据通道、v0.3.4 缺口补齐）

## 项目定位

面向中国 A 股的策略回测系统。数据层用 Python，回测引擎用 Go。

引擎目标是**通用、模块化、可单步**，最终支撑三类使用场景：

1. **交互式单步调试** —— Web 端配置参数，逐步推进，查看每一步的信号、订单、成交与账户变化
2. **批量策略海选** —— 批量传入配置列表并发回测，输出稳健参数区域
3. **实盘预测** —— 用同一套引擎与策略代码，产出「今日动作」

### 当前范围

| 维度 | 当前范围 | 远期 |
|---|---|---|
| 市场 | 仅 A 股 | 美股、日经、加密货币 |
| 频率 | **仅日线**（Web 端向用户明示） | 分钟线（随远期市场一并引入） |
| 标的 | 个股 + **ETF** | —— |
| 因子 | **纯技术面**（量价） | —— |

「纯技术面」是明确的范围约束：不采集、不存储、不计算市盈率、市净率、
财报等基本面数据。这会显著简化 schema 与 ETL，也意味着策略层不应出现基本面信号。

## 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 数据获取 | Python + **BaoStock（个股）/ 新浪（ETF、复权因子）** | 见下方数据源分工；东财因限流弃用 |
| 数据存储 | Parquet（列式文件） | Python 与 Go 的唯一耦合点是 **schema**，不做 cgo / gRPC 互调，边界越薄越好 |
| 回测引擎 | Go 1.26+ | 事件驱动模型下 Go 的性能与类型安全是关键收益 |
| 策略形态 | **Go 原生编译** | 策略实现 `Strategy` interface 编译进引擎；Web 端配参数不写逻辑 |
| 数据频率 | **仅日线** | 时间模型仍按多频率设计（见 C9），但当前只实现日线 |
| 结果库 | DuckDB | 海选结果存储与查询 |

### 数据源分工（依据 v0.0 实测，详见 `docs/probe/REPORT-v0.0.md`）

| 数据 | 来源 | 理由 |
|---|---|---|
| 个股日线（含退市股） | **BaoStock** | 唯一同时提供 `preclose` / `tradestatus` / `isST` 的源；无限流 |
| point-in-time 股票池 | **BaoStock** `query_all_stock(day=)` | 直接支撑约束 C3 |
| 个股复权因子 | **新浪** `adjust="hfq-factor"` | 16 位精度事件式因子，实测还原误差 < 1e-6 |
| ETF 日线 | **新浪** `fund_etf_hist_sina` | BaoStock 无 ETF 行情；新浪覆盖全历史 |
| ETF 复权 | ✅ 已收口（v0.1） | 从事件日价格跳变反推因子，见 ETL.md §6.9 |
| 交易日历 | BaoStock / 新浪均可 | —— |
| 分红送配 | BaoStock | 字段最全（登记日/除权日/派息日/送股/转增） |

> **东财弃用**：`push2his.eastmoney.com` 约 10 次请求即触发 IP + 端点级封禁，
> 实测 **≥45 分钟未恢复**（探针跑满上限，真实时长未测出），无法支撑批量 ETL。
> 按此速率回补 1647 只 ETF 需 120 小时以上，故也不再作为 ETF 复权的首选退路。

## 核心设计约束

以下几条是**架构级不可妥协项**，任何版本的实现都不得违反。

### C1. 未来函数防护

策略**绝不能拿到全量数据切片**，必须通过带时间游标的 `DataGateway` 访问，只能读到 `<= 当前决策时点` 的数据。用 Go 的类型系统在**编译期**禁止越界访问，而不是靠自觉。

### C2. 复权处理

**存原始价 + 复权因子**，引擎内部按需动态复权。

前复权价格会随每次新的除权事件变化 —— 昨天算出的信号今天就变了，既导致回测不可复现，本身也是一种未来函数。分红送股必须真实反映到账户（现金分红入账、送股增加持仓），而不是只调整价格。

### C3. 幸存者偏差

股票池**必须包含已退市股票**，否则回测收益系统性虚高。指数成分股必须是 point-in-time 的（回测 2019 年时用的是当时的沪深 300 成分，而非今天的）。

### C4. 引擎核心是状态机

核心必须是 `Step() (Event, error)` 的状态机，**不能是内部的 for 循环**。单步调试、批量海选、实盘增量三种模式共用同一个核心，只换 Driver 与 Recorder。

写成 for 循环后再改状态机等于重写，此约束在 v0.2 落地时必须严格遵守。

### C5. 可复现性

`配置哈希 + 数据版本 + 引擎版本 → 结果指纹`。同配置两次运行必须**逐笔一致**。海选出的策略必须能一键重跑复现，否则海选没有意义。

### C6. 回测—实盘一致性

「今日动作」本质上是**回测跑到今天再多跑一步**。同一份策略代码、同一个引擎核心，只替换 `DataFeed`（历史→实时）与 `Executor`（模拟成交→信号输出）。

这要求引擎状态**可序列化 / 快照恢复**，否则每天实盘都要从头重算多年数据。

### C7. 过拟合防护

跑 1000 组参数，排名第一的那组大概率是运气（多重检验问题）。

**海选的输出不是「排名第一的参数」，而是「稳健的参数区域」。** 必须支持样本内/样本外切分（IS/OOS）、Walk-Forward 滚动验证、参数高原邻域稳健性评分。

### C8. A 股交易规则

以下规则内建于 `Market` / `Broker` / `Fee` 模块，且**必须按标的类型分流**——
个股与 ETF 的成本模型不同，同一策略跑两者会得出不同结论。

| 规则 | 个股 | ETF |
|---|---|---|
| 印花税 | 卖出 0.05% | **免征** |
| 过户费 | 沪深双向 0.001% | **免征** |
| 佣金 | 万 2.5，最低 5 元 | 同左（费率可能更低） |
| 交收 | T+1 | 股票型 T+1；**跨境 / 黄金 / 债券 T+0** |
| 涨跌停 | 主板 10% / 创业板科创板 20% / ST 5% / 北交所 30% | 10%；跟踪创业板科创板指数的为 20% |
| 最小单位 | 买入 100 股整数倍，卖出可零股 | 100 份起，100 份为单位 |

共同规则：

- **一字板无法成交**：需在撮合器中建模，不能假设总能成交
- **停牌**：不产生成交，由 `tradestatus` 标记识别
- **成交量约束**：单笔成交不超过当日成交量的 X%，避免对流动性差的标的产生不真实的大额成交

#### C8.2 涨跌幅规则有时间维度 ⚠️

涨跌幅限制**不是常量**，随监管规则变更。已确认的生效日：

| 生效日 | 变更 |
|---|---|
| 2026-07-06 | 沪深北新版交易规则，主板风险警示股（ST/*ST）由 **5% → 10%** |
| 2020-08-24 | 创业板注册制改革，由 **10% → 20%** |

两者均由 v0.1 的板块自洽校验从数据中发现后查证确认
（详见 [ETL.md](ETL.md) 6.6）。**Market 模块必须按日期分段实现**，
写成静态常量会导致回测 2026-07-06 之前的 ST 股放行本该被拦截的成交。

参考实现：`etl/build_bars.py: limit_ratio(board, is_st, trading_day)`。

#### C8.3 明确不建模的机制

- **集合竞价**：不建模竞价阶段的订单排队、价格发现与可撤单窗口。

  这一决定与「仅日线」的范围是自洽的 —— 日线数据本就不含竞价阶段的委托明细，
  即便想建模也无数据支撑。实际影响仅限于：`ts_open` 取 09:30（连续竞价开始）
  而非 09:25；Broker 把开盘价、收盘价当作**成交价假设**使用，
  而不模拟产生这些价格的撮合过程。

  一字板仍然建模 —— 它依赖的是涨跌停价与成交量，不依赖竞价机制。

#### C8.1 涨跌停基准必须用 `preclose` ⚠️

**涨跌停价的基准是「除权调整后的前收盘价」，不是前一交易日的实际收盘价。**

v0.0 实测证据（详见 `docs/probe/REPORT-v0.0.md` 2.3）：

| 标的 | 日期 | 前一日收盘 | 按前收算的跌停 | 实际最低 |
|---|---|---|---|---|
| 002594 比亚迪 | 2025-07-29（除权日） | 337.00 | 303.30 | **109.77** |
| 300750 宁德时代 | 2023-04-26（除权日） | 385.90 | 308.72 | **210.01** |

若用 `close.shift(1)` 推导涨跌停价，Broker 会在每个大比例送转的除权日
误判「跌停不能卖 / 涨停不能买」。大比例送转每年都有，不是边缘情况。

→ `bar` 表必须存 `preclose` 字段（A 股扩展列）。

### C9. 数据源与市场的独立性

数据源适配器不是「将来可能要换」的预留，而是**核心设计**：v0.0 已经导致
主力源从 AkShare 换成 BaoStock，且 ETF 与个股走的是不同的源。

- **数据源可换**：新增或替换数据源不得改动 DataGateway 以上的任何代码
- **市场可扩**：接口按多市场设计，实现只做 A 股。接口中不得出现写死的
  `涨跌停 10%`、`T+1`、`100 股整手`、`9:30-15:00` 这类常量 —— 它们属于
  某个 `Market` 实现的配置，而非引擎的假设
- **频率可扩**：当前只实现日线，但时间模型保持多频率形态（`Bar` 带 `Freq`，
  `Step()` 步进单位是「下一个事件时点」而非「下一天」），以便远期接入
  美股 / 日经 / 加密货币的分钟线时无需重构核心

远期市场的已知差异（接口设计时需容纳，当前不实现）：
T+0 交收、做空、无涨跌停、24×7 连续交易、非整数最小交易单位、多币种。

### C10. 纯技术面

引擎只消费量价数据。不采集、不存储、不计算市盈率、市净率、财报等基本面字段。

这一约束同时作用于 schema（`bar` 表不含估值列）、ETL（不拉财务接口）
与策略层（不应出现基本面信号）。

## 架构分层

```
┌─────────────────────────────────────────────────┐
│  Python ETL   AkShare/... → Parquet             │  ← 唯一耦合点：schema
└─────────────────────────────────────────────────┘
                      ↓  (文件)
┌─────────────────────────────────────────────────┐
│  DataGateway   时间游标 · 复权 · 未来函数防护     │
├─────────────────────────────────────────────────┤
│  Core Engine   Step() 状态机 · 事件总线           │
│  ┌──────────┬──────────┬──────────┬───────────┐ │
│  │ Market   │ Broker   │ Portfolio│ Recorder  │ │
│  │ 日历/规则 │ 撮合/滑点 │ 账本      │ 三档记录   │ │
│  ├──────────┼──────────┼──────────┼───────────┤ │
│  │ Fee      │ Sizer    │ Risk     │ Metrics   │ │
│  └──────────┴──────────┴──────────┴───────────┘ │
│         全部 interface + registry 装配            │
├─────────────────────────────────────────────────┤
│  Driver   StepDriver（交互） │ BatchDriver（海选） │
├─────────────────────────────────────────────────┤
│  API      HTTP / WebSocket                       │
└─────────────────────────────────────────────────┘
```

### 模块职责边界

| 模块 | 性质 | 职责 |
|---|---|---|
| `Market` | 配置 | 交易日历、交易规则、涨跌停计算、停复牌；**按标的类型分流**（个股 / ETF） |
| `Broker` | 行为 | 订单 → 成交，处理涨跌停/停牌/成交量约束/滑点 |
| `Portfolio` | **状态（账本）** | 现金、持仓、可用/冻结、权益、盈亏、除权除息入账 |
| `Sizer` | **决策（策略侧）** | 给定信号计算下单数量 |
| `Risk` | 行为 | 下单前拦截：单票上限、集中度、回撤熔断 |
| `Fee` | 配置 | 佣金、印花税、过户费；**按标的类型分流**（ETF 免印花税与过户费） |
| `Recorder` | 观测 | 三档级别记录（None / Summary / Full） |
| `Metrics` | 观测 | 绩效指标计算 |

> `Portfolio`（账本，是状态）与 `Sizer`（仓位决策，是策略侧）必须分离。
> 混在一起是回测框架最常见的架构债。

### 关于「热插拔」

Go 的 `plugin` 包**在 Windows 上完全不支持**，且要求主程序与插件用完全相同的 Go 版本和依赖版本编译，实践中极其脆弱。

本项目采用 **接口 + registry + 配置装配**：各模块定义 interface，实现在 `init()` 中注册到全局 registry，运行时按配置中的字符串选择实现。

```json
{ "fee": "a_share_2023", "slippage": "fixed_bps", "sizer": "equal_weight" }
```

效果上达成「任意组合」，代价仅是新增实现需重新编译（编译耗时约 2 秒，可接受）。

若后续确实需要不重编译即可改策略逻辑，那是**脚本层**（表达式引擎 / Starlark / WASM）的事，不是 plugin 的事，视需要在 v1.0 之后评估。

## 数据存储设计

### 选型：本地 Parquet 文件，不引入数据库

依据 v0.0 的 P8 / P9 基准（30.7 万行真实样本，详见 `docs/probe/REPORT-v0.0.md`）。

**理由是访问模式，不是体积。** 回测不做随机点查，而是「一次加载、反复顺序扫描」：
全市场 2000 万行日线约 **350 MB**，载入内存后所有访问都是指针运算。
数据库的索引、事务、MVCC、连接池在这个场景全是纯开销。

更关键的是海选场景：**N 个 worker 共享同一份只读内存数据，零拷贝** ——
这是 Go 相对 Python 的核心优势，数据放进数据库这个优势就消失了。

同时 Parquet 是云上一等公民：对象存储直接放，DuckDB / Athena / BigQuery / Spark
都能直查，支持 range request 按行组读取，Hive 分区被普遍识别。

### 实测结论

| 变体 | 字节/行 | 全市场外推 | vs 基线 |
|---|---|---|---|
| **定点整数 + DELTA_BINARY_PACKED + zstd** | **18.30** | **349 MB** | 0.61x |
| 定点整数 + zstd(L9) | 22.64 | 432 MB | 0.76x |
| 定点整数 + zstd(L3) | 23.03 | 439 MB | 0.77x |
| float64 + zstd | 24.52 | 468 MB | 0.82x |
| float64 + snappy | 29.77 | 568 MB | 1.00x |

跨语言链路三个方向全部实测通过：Python 写 → Go 读（6/6 变体校验和一致）、
Go 写 → Python 读（含可空/布尔/字符串字段）、`CGO_ENABLED=0` 编译通过。

**保守子集原则**：只用各语言实现都成熟支持的压缩（zstd）与编码
（dictionary / plain / RLE / DELTA_BINARY_PACKED，后者已实测 Go 可读）。
不为多省几个百分点使用冷门编码 —— 那正是跨语言兼容性出问题的地方。

### 跨市场统一 schema

范围要求兼容远期的美股、期货、加密货币。P9 实测：统一 schema 仅比
A 股专用 schema 大 **2.0%**（356 MB vs 349 MB），跨市场兼容近乎免费，
因此**直接采用统一 schema，不做 A 股专用版**。

> **已兑现（v0.3.3）**：接 OKX 永续合约时，bar 的 10 个核心列与 4 个
> A 股扩展列**一列没改**，Go 的 loader 也一行没改就读出了加密分区。
> 需要改的只有三处：新增四个枚举值、`price_scale`/`qty_scale` 取不同值、
> `tradestatus` 的语义从「停牌」推广为「该 bar 不可成交」。
>
> 唯一真正暴露的缺陷是 **`price_fp × qty_fp` 会溢出 int64**
> —— 它一直存在，只是 A 股的 scale 太小（1e3 × 1e0）掩盖了它。
> 这正是「接第二个市场」的价值：**一个市场验不出跨市场抽象**。

#### 层 1：bar 核心 10 列 —— 全市场严格统一

```
instrument_id  int32     引擎内部 ID，非 symbol
ts_open        int64     UTC 毫秒，bar 起始时刻（策略侧不得使用）
ts_close       int64     UTC 毫秒，bar 结束时刻（时间游标用此列）
trading_day    int32     YYYYMMDD，业务语义的交易日
open/high/low/close  int64   定点整数
volume         int64     定点整数
amount         int64     计价币种最小单位
```

引擎核心循环只读这 10 列，其名称与语义**不可变更**。
逐字段定义见 [SCHEMA.md](SCHEMA.md)。

#### 层 2：市场特定列 —— 直接附于同表

```
ashare  : + preclose, turn, tradestatus, is_st
us      : + preclose, pre_market_volume
futures : + open_interest, settlement
crypto  : + funding_rate
```

该方案的前提「Go 可用仅含核心列的 struct 读取扩展列文件」已由
`engine/cmd/subsetread` 实测验证通过，因此**无需拆分扩展表做 join**
（分表方案实测多占 1.3% 体积且读取更复杂）。

Go 侧对应两个 struct：`CoreBar`（跨市场通用）与 `AShareBar`（含扩展列）。

#### 层 3：instruments —— 统一列 + `attrs` JSON

```
instrument_id, market, symbol, name, type,
price_scale, qty_scale, quote_ccy,
list_date, delist_date, board,
attrs  string(JSON)   市场特定属性
```

`attrs` 承载期货的到期日与合约乘数、加密的基础币种与合约类型。
instruments 仅数万行，全量载入内存后解析 JSON 无性能顾虑，
换来的是 **schema 稳定：新增市场不改表结构**。

### 关键类型决策

| 决策 | 理由 |
|---|---|
| 价格用 **int64 定点**而非 float64 | **不是为了体积**（实测仅省 6%），而是约束 C5 可复现性：浮点累加顺序不同结果不同，并发海选下无法保证逐笔一致。加密还需跨 13 个数量级的精度 |
| `price_scale` / `qty_scale` 存于 instruments | A 股 1e3 够用，加密需 1e8；每标的自带 scale，引擎按标的解释 |
| `ts_open` / `ts_close` **两端都存** | 数据源惯例相反（Binance kline `[0]` 与 OKX `ts` 均为**开始时刻**），而引擎的时间游标需要的是「信息可得时刻」= 结束时刻。只存一端就要推导另一端，而 A 股日线时长非固定时段（含午休），推导正是未来函数 off-by-one 的高发处。用**字段名**消除歧义，实测代价 +1.22% |
| `trading_day` 与时间戳并存 | 时间戳用于跨市场对齐、加密 24×7、美股夏令时；`trading_day` 用于业务语义。delta 编码后冗余代价近乎为零 |
| 用 `instrument_id` 而非 symbol | 跨市场 symbol 会冲突；4 字节整数比字符串 cache 友好，实测反而净省空间 |

### 明确不纳入数据 schema 的三项

1. **交易规则**（涨跌停、T+1、保证金、最小变动价位）→ 属 `configs/market/*.json`，是 Market 模块配置
2. **复权因子** → 仅对股票 / ETF 有意义。期货的「主力连续」是拼接规则生成的**派生数据**，应作为独立合成标的，与复权无关
3. **多空与杠杆** → 属 Portfolio / Broker 模块

### 目录布局

`data/` 不进 git，因此布局由代码定义、可一键重建 ——
**单一事实源是 [`etl/layout.py`](../etl/layout.py)**，各处不得硬编码路径字符串。

```
data/                                     gitignored
├── bar/market=ashare/freq=1d/year=YYYY/  行情，Hive 分区
├── meta/                                 元数据表（Parquet + CSV 镜像）
│   ├── instruments.parquet  + .csv
│   ├── calendar.parquet     + .csv
│   ├── adj_factor.parquet   + .csv
│   └── corporate_action.parquet + .csv
├── results/                              海选结果，Go 引擎写入
│   └── equity/                           净值曲线分片
├── snapshots/                            引擎状态快照（v0.4）
└── cache/                                ETL 中间缓存，可安全删除
configs/                                  进 git
├── fee/  market/  strategy/
```

一键重建：

```bash
python etl/layout.py
```

### CSV 镜像规则

**元数据表同时输出 CSV 镜像**：Parquet 为权威副本，CSV 仅供人眼检查与 diff。

- 适用范围：仅 `META_TABLES` 四张元数据表；bar 表体量 2000 万行级，**不做镜像**
- **任何程序都不得读取 CSV** —— 它是调试产物，不是数据接口
- 由 `etl/layout.py: write_meta()` 统一写出，避免各处各写一份

### 数据源与格式的分界

```
数据源 ETL 产出  →  Parquet   （data/，gitignored）
人手写的配置     →  JSON      （configs/，进 git）
```

配置用 JSON 而非 YAML：Go 标准库原生支持，无需第三方库；
且 v0.3 的 ParamSpec 需生成 JSON Schema 供 Web 端表单使用，格式统一。

### 一个被省掉的表

原计划的 point-in-time 股票池表**不需要**：BaoStock 停牌日照常返回行，
因此 `bar` 表本身即是 point-in-time 的 ——
`某日股票池 = SELECT DISTINCT instrument_id FROM bar WHERE trading_day = d`。
上市前无行、退市后无行、停牌有行且 `tradestatus=0`，语义完整。

若按每日快照单独存表，7200 × 8000 天 ≈ **5760 万行，比 bar 表还大**，纯浪费。

### v0.3 ✅ — 模块化装配（已完成 2026-08-29）

**目标**：配置驱动装配 + Web 表单的元数据基础。
设计与评审决议见 [DESIGN-v0.3-assembly.md](DESIGN-v0.3-assembly.md)，分三刀。

**第一刀 ✅ registry + 配置装配 + Sizer + Risk**

- `internal/spec` —— `ParamSpec` 从 engine 下沉，供所有域自描述
- `internal/registry` —— **泛型**容器，不认识任何领域类型（否则 trading 与它互相 import 成环）
- `internal/config` —— 一份 JSON 描述一次运行，`-config` 取代全部命令行开关
- `Sizer` 5 个实现 / `Risk` 4 个实现，风控**链式**执行
- `Strategy.OnBar` 改出 `Signal`：策略只说买什么卖什么，数量归 Sizer、限额归 Risk
- 三个样例策略随之变薄（`buy_and_hold` 连参数都没有了）

回归：对照组 `buy_and_hold` 与 v0.2 **逐分位一致**；
另两个策略的差异经归因验证只来自一处有意的修正（槽位计数去重）。

**滑点修正**（插在两刀之间）：原实现把滑点加在单价上，而价格单位是厘，
5 bp 在 20 元以下的标的上不足一厘 —— 三种取整方向实测分别给出
3.67 / 5.34 / 5.63 bp，配置写的是 5.00。改为**按成交额计成本**后精确。
附带让滑点在账本里可见：`macd_cross` 的滑点 8.89%，与全部费用（11.56%）
同一量级，以前完全隐形。

**第二刀 ✅ Recorder + Metrics**

- `internal/record` —— 三档记录，由**引擎**持有（三种驱动模式共用一个核心，C4）
- `internal/metrics` —— 年化 / 波动 / 夏普 / 索提诺 / 最大回撤 / 卡玛 /
  胜率 / 盈亏比 / 换手 / 基准对标
- `MatchRoundTrips` —— FIFO 逐层配对，送股零成本入队，未平仓不计入胜率
- **年化系数由日历数出**（实测 242.54 / 242.97），不是 252

验收：5 个交易日 + 3 笔来回的手工核算与实现逐位一致。

**第三刀 ✅ 结果指纹（C5）**

- `internal/fingerprint` —— 数据指纹**哈希内容**而非 mtime
  （复制一份目录不该改变指纹），按 `(路径,大小,mtime)` 缓存
- 配置规范化：只含影响结果的字段。`name` / `recorder.level` / `metrics.*` /
  `data.root` 都不进
- 输出指纹在**引擎内**滚动计算，故不受记录级别影响；滚动状态进快照，
  否则实盘每日从快照恢复后指纹永远对不上

验收矩阵实跑通过：同配置两次相同；改 `slippage.bps` 两个指纹都变；
改 `recorder.level` / `name` / `metrics` 两个指纹都不变。
快照往返现在比对指纹而非账本三个数 —— 账本相同只说明结果相同，
指纹相同才说明逐笔成交都相同。

- registry + `init()` 注册，JSON 配置装配
- **ParamSpec 参数自描述**：策略注册时声明参数名称/类型/范围/步长/默认值

  ```go
  func (s *MACross) Params() []ParamSpec {
      return []ParamSpec{
          {Name: "fast", Type: Int, Default: 5,  Min: 2, Max: 60,  Step: 1},
          {Name: "slow", Type: Int, Default: 20, Min: 5, Max: 250, Step: 1},
      }
  }
  ```

  该机制同时支撑三处：Web 自动生成表单（v0.4/v1.0）、海选自动展开参数网格（v0.6）、配置校验。
- `Sizer` / `Risk` / `Slippage` / `Fee` 全部可替换
- `Recorder` 三档级别（None / Summary / Full）
- 完整指标集：年化收益、夏普、索提诺、最大回撤、卡玛、胜率、盈亏比、换手率、基准超额
- 结果指纹（C5）

**验收**：换 JSON 配置即可改变引擎行为 ✅；同配置两次运行结果逐笔一致 ✅
（由输入/输出指纹机器可验，不靠肉眼比对汇总数）。 **量级 M**

把 v0.3.3 记下的缺口和评审搁置的决策一起收掉。

#### 做了什么

| | 事 | 结果 |
|---|---|---|
| 1 | **`funding` 表** | 永续资金费率，8h 原始粒度不聚合。577 行 |
| 2 | **年化系数移到 `Market.AnnualDays()`** | A 股走日历实测 242.54，24×7 返回 365；不再写死 `MarketAShare` |
| 3 | **`min_turnover` 流动性风控** | 成交额门槛 + 单笔占比上限。**只拦买入** |
| 4 | **两个正交策略** | `rsi_reversion`（均值回归）、`donchian_breakout`（突破） |
| 5 | **标的池含退市股** | 3,193 只在市 → 3,376 只（C3） |

#### 🔴 这一版最重要的发现：单次回测的收益率读不出策略的好坏

补完流动性风控后做了一次门槛敏感性扫描（`macd_cross`，在市主板，
其余参数完全不动，只改成交额门槛）：

| 门槛（万元） | 风控拒单 | 总收益 | 输出指纹 |
|---|---|---|---|
| 0 / 50 / 100 / 200 / 300 | 0 | **+31.92%** | `1f91e97a5032`（五者**逐位相同**） |
| 500 | **1** | +24.46% | `eee2aa3a90ad` |
| 1000 | 18 | **+14.90%** | `248c9856dcdc` |
| 2000 | 52 | **+26.73%** | `01b55d85102e` |

**一笔拒单，收益移动 7.5 个百分点。而且非单调** —— 2000 万的门槛比
1000 万好 11.8 个点。这不是「风控有代价」，是**路径依赖**：
10 个仓位在 3,376 只标的里选，一个决策变了，后面全部重排。

以为是仓位太集中，把 `slots` 从 10 提到 50 重测 —— **极差反而从 17.0
个点涨到 23.7 个点**，收益从 +31.92% 掉到 +2.19%。不是集中度的问题。

**三条结论：**

1. **本项目此前所有单次回测的数字，都不足以支撑策略间的比较。**
   包括这份文档里记的那些。它们是可复现的（指纹一致），但不是稳健的 ——
   可复现说的是「同配置同结果」，稳健说的是「邻近配置也是类似结果」，
   两者是不同的性质，而后者不成立。
2. **海选按单次收益排序 = 排运气。** 这把 C7 从「防过拟合的加分项」
   变成了「读懂结果的必要条件」。
3. 报告里应当出现的不是一个收益率，而是**一族邻近配置的收益分布**。

> 这个发现是补流动性风控时**顺手撞见**的 —— 本来只想确认风控没写错。
> 教训与 ETL.md 6.10（分母取错）、v0.3 的滑点三次返工同源：
> **不要相信一次测量，尤其当它符合预期的时候。**

#### 幸存者偏差实测（2×2 隔离）

`macd_cross`，2020-01 起，主板个股：

| | 在市（3,194） | 含退市（3,376） |
|---|---|---|
| **无流动性风控** | +31.92% | **+8.26%** |
| **有流动性风控** | +8.51% | −11.99% |

含退市单独的影响是 **−23.66 个百分点**，流动性风控单独是 −23.41。
8.4% 的样本造成 24 个点的偏差 —— 远超样本占比，因为退市股贡献的是
分布的左尾（先大跌再退市）。

**但按上一节的结论，这两个数字本身也带着路径依赖的噪音，
方向可信，幅度不可尽信。**

#### 四个策略在标准池上的表现

含退市 3,376 只主板个股，成交额门槛 500 万，2020-01 起，基准 510300（+26.31%）：

| 策略 | 类别 | 成交 | 总收益 | 超额 | 回撤 | 夏普 | 摩擦 |
|---|---|---|---|---|---|---|---|
| `rsi_reversion` | 均值回归 | 166 | **+2.45%** | −23.86% | 28.29% | 0.033 | **1.9%** |
| `macd_cross` | 趋势 | 1,424 | −29.66% | −55.97% | 55.71% | −0.188 | 16.4% |
| `ma_cross` | 趋势 | 1,560 | −32.76% | −59.07% | 46.81% | −0.251 | 17.7% |
| `donchian_breakout` | 突破 | 919 | −69.04% | −95.35% | 80.21% | −0.574 | 10.5% |

四个全部跑输基准。**摩擦与成交笔数几乎线性** —— `rsi_reversion` 交易少
所以摩擦只有 1.9%，这是它唯一的优势，而它依然跑输「什么都不做」。

同样地：这些是单点估计，按上一节的结论**不能据此给策略排名**。
它们的作用是说明「四类思路在默认参数下都不明显有效」，仅此而已。

#### 四项收尾（2026-08-29 拍板）

**① 资金费率：统一忽视，但必须显式披露。**
不做「有数据的段算、没数据的段不算」—— 那会让同一次回测的两段用不同的
成本模型，而报告上看不出异常。于是新增 `Config.Disclosures()`：
返回本次回测**已知未计入**的成本与机制，CLI 报告印一段「本次回测未计入」，
Web 端在绩效同屏显示。

> 为什么要专门造个机制而不是写句注释：报告上的每个数字都在说
> 「发生了什么」，**没有任何一处在说「什么没算」**。v0.3 的滑点就是
> 这样藏了很久 —— 混在成交价里，直到单列才发现它有 8.89 万元。
> 只存在于源码注释里的缺口，等于不存在。

**② 每 worker 的引擎常驻：实测完毕，顺带修掉一个 4.8 倍的浪费。**

新增 `cmd/enginebench`（与 `loadbench` 平行）。第一次测出来
「每 worker 400 MB」，与共享数据 375 MB 同量级 —— 不对劲，查下去发现
`Config.narrow` 的判据是**标的集完全相等**才透传，而含退市股的池子上
这个条件**永远不成立**：`ResolveUniverse` 按 instruments 表给 3,485 只
主板个股，2020 年后真有行情的只有 3,375 只。于是每次 `Assemble`
都重新 `Subset` 一份，实测 **358 MB**。

判据放宽成「col 里的标的都在 ids 里」（子集关系）后：

| worker | 每次 Subset | 共享子集 |
|---|---|---|
| 1 | 1,090 MB | 732 MB |
| 4 | 2,173 MB | 740 MB |
| 8 | **3,615 MB** | **751 MB** |

边际成本从 **361 MB/worker** 降到 **2.7 MB/worker**，8 worker 墙钟
5.70 s → 3.75 s。结论：

> **内存不是海选的瓶颈，前提是 BatchDriver 预先裁一次子集。**
> 固定开销 375（共享数据）+ 358（子集）MB，之后每个 worker 只要 2.7 MB。
> 100 个 worker 约 1 GB —— 真实上限是 CPU 核数。
> 不预裁的话 8 个 worker 就是 3.6 GB，共享只读内存的优势直接归零。

**③ 回测区间早已可配**（`data.from` / `data.to`，Web 的 JSON 编辑器里
也能直接改）。补测全历史确认跑得动：

| 区间 | 标的 | 行数 | 步数 | 引擎耗时 |
|---|---|---|---|---|
| 2020-01 起 | 3,376 | 506 万 | 1,614 | 2.5 s |
| **2005-01 起（21.65 年）** | **3,461** | **1,246 万** | **5,260** | **8.1 s** |

按此推算 Walk-Forward 的代价：18 个窗口 × 每窗约 4 年（≈1,000 步 ≈1.5 s）
= 每组参数约 27 s，300 组 8 worker 约 17 分钟。可行。

> 全历史跑出来总收益 +0.58%、最大回撤 **72.63%**（2008-01 → 2012-12，
> 1,190 个交易日）。基准覆盖只有 65.89% —— 宽基 ETF 最早 2012 年，
> 报告已显式标注「未覆盖区间不计超额」。

**④ `grid` 保留**，不从策略池里删。

**验收**：三个 A 股基线配置的输出指纹**逐位不变**
（`cfa21186f91114e2` / `d5b086a194c97ac4` / `527df089655d1298`，
后两个已于 2026-08-30 因修 crossState 的假金叉而变更，见上）——
年化重构、`narrow` 判据放宽、新增风控与策略，都没有动到既有行为。 **量级 M**

### v0.4 ✅ — 单步调试（2026-08-30）

**目标**：需求 3 —— 单步运行与细节记录。

回测视图回答「跑完是什么样」，单步回答**「这一天为什么是这个决定」**。
两者要看的东西完全不同：跑完只需要成交记录，单步需要看到整条漏斗。

#### 做了什么

| | 事 |
|---|---|
| 引擎 | 补 8 个只读入口：`Pending` / `Now` / `PeekAt` / `NumSteps` / `IndicatorKeys` / `IndicatorAt` / `BarAt` / `AvailableAt` |
| 服务端 | `session.go` —— 会话管理、事件捕获、标的检视、快照读写 |
| 接口 | `POST /api/session`、`{id}/step`、`{id}/reset`、`{id}/inspect`、`{id}/snapshot`、`{id}/restore`、`DELETE {id}` |
| Web | 新增「单步调试」视图：步进控制 + 漏斗事件流 + 标的检视 + 持仓/在途 |

#### 三个设计决定

**① 纯 HTTP，不用 WebSocket**（与本节原计划不同，理由如下）。
步进是**用户驱动的请求/响应** —— 点一下走一步，等的就是这一步的结果。
WebSocket 换来的是「服务端主动推」，而这里没有服务端主动产生的事件；
代价是一整套连接生命周期、重连、断线后的状态对齐。
长跑最坏 5,260 步约 8 秒，一次请求扛得住。

真需要推送的是 v0.6 实盘：那时事件由行情驱动，服务端确实要主动说话。
**那时再加**，比现在为一个用不上的能力先背上协议复杂度划算。
（原验收「wscat 能驱动一次回测」相应改为 curl。）

**② 会话驻留一台引擎，不做「重放到第 N 步」。**
引擎状态（指标、账本、在途队列）无法从「第 N 步」这个数字重建 ——
只能从头跑。每次步进都重放在 5,260 步上是 8 秒。
代价是内存，而 v0.3.4 已测出每个引擎边际只要 2.7 MB
（大头是标的池子集，由 `narrowCached` 在同池子的会话间共享）。
同时最多 8 个会话，超了**拒绝新建而不是 LRU 淘汰** ——
调试会话里有用户攒下的状态，悄悄淘汰比报错难受得多。

**③ `until` 断点比「再走 N 步」有用得多。**
调试时真正想问的是「下一次成交发生在哪天、为什么」。
`{"until":"signal"|"fill"|"reject"}` 三个断点 + `{"day":YYYYMMDD}`，
谁先到停在谁。没有它，用户只能一步一步点过去，在 1,614 步上不现实。

配套的一条：**无事发生的步不产生事件**，只计数。
走 500 步时要看的是「哪几天有事」，不是 500 份空表。

#### 漏斗是这一版的核心

```
信号 → 定量(Sizer) → 风控 → 入队 → 撮合 → 成交 / 拒单
```

每一环都可能把单子吃掉，而**只看成交记录时全部表现为「什么也没发生」**。
四段并排摆出来，一眼能看出单子死在哪一环。实跑 `macd_cross` 的三个例子：

| 现象 | 一眼可见的原因 |
|---|---|
| 步 40：**18 个信号 → 0 个订单** | Sizer 没给额度 —— 10 个仓位满了，现金只剩 2.0 万 |
| 步 35：238 信号 → 10 单 → **0 成交** | 单进了队列等 T+1，次日（步 36）开盘全部成交 |
| 步 47：3 信号 → 3 单 → 2 成交 **2 拒单** | 600156「涨停买不进：参考价 7.030 已达涨停 7.030」，随后「超过有效期」 |

标的检视再往下钻一层，把当日 bar、涨跌停价、**指标值与是否就绪**、
持仓、可卖、在途摆在一起 —— 600156 在 2020-03-16 的答案是
「最高 7.030 = 涨停价，MACD 已金叉（DIF 0.6797 > DEA 0.6370），
但买不进」。少任何一项这句话都说不完整。

> 一处刻意的克制：指标**未就绪时不显示数值**，只显示「预热未完成」。
> 把未就绪的指标画成 0，会让人以为「指标是 0 所以没信号」，
> 而真相是「还没算出来」。调试时这两件事天差地别。

#### 快照

存档/读档跑通了，并且**这是快照第一次进真实工作流**（此前只在单测里验过）。
实测往返：第 47 步存档 → 再走 50 步（第 97 步，权益 952,499.72，持仓 7）
→ 读档回第 47 步 → 再走 50 步，**四项逐位一致**。
它同时是 v0.6 实盘「每日从昨天恢复」的同一个能力。

**验收**：curl 能完整驱动一次回测，每步细节可见；
三个 A 股基线的输出指纹**逐位不变**
（`handleBacktest` 改为与会话共用 `assembleFor`，是行为保持的重构）。 **量级 M**

- **IS/OOS 切分 + Walk-Forward 滚动验证**（C7）
- **参数高原稳健性评分**：看邻域参数是否同样表现良好，而非单点尖峰

#### 已定（2026-08-29 评审）

**① 规模：计算不是瓶颈。** 实测全池一次回测 **2.796 s**
（3,194 只 / 1,614 步 / 490 万行），数据载入 29.4 s 一次性、
N 个 worker 共享同一份只读内存。1,000 组 8 worker 约 6 分钟，
10,000 组约 1 小时。数据常驻：全量 1.25 GB，2020 起主板子集约 392 MB。

**已测**（v0.3.4，`cmd/enginebench`）：固定开销 375 MB（共享只读数据）
+ 358 MB（标的池子集），之后**每个 worker 只要 2.7 MB**。
100 个 worker 约 1 GB，真实上限是 CPU 核数不是内存。

⚠ **前提是 BatchDriver 预先裁一次子集并复用。** 不这么做的话每个
worker 各拷一份 358 MB，8 个就是 3.6 GB —— 共享只读内存的优势归零。
服务端的 `narrowCached` 已经是这个形态，照抄即可。

**② 网格：范围可自定义，先粗后细。** 配置里显式写取值，不是让引擎
按 spec 的 `[Min, Max]` 全撒 —— `macd_cross` 的合法空间有 670 万组，
全撒一定能找出一组「历史上完美」的参数，而它一文不值。
先跑一个可辩护的粗网格（如 macd 75 组 × sizer 4 组 = 300 组，8 worker 不到 2 分钟），
**发现高原后再在高原附近加密**。

**③ Walk-Forward：IS 3 年 / OOS 1 年 / 步进 1 年。**
实测全历史一次回测 8.1 s（5,260 步 / 1,246 万行 / 3,461 只），
每窗约 4 年 ≈ 1.5 s，18 窗 ≈ 27 s/组参数；300 组 8 worker 约 17 分钟。
全量数据 5,260 个交易日（2005-01-04 ~ 2026-08-28，21.6 年），
可切出 **18 个窗口**。IS 约 730 天，足够 MACD(26) 预热且样本充足；
18 段 OOS 才看得出「稳定有效」还是「只在某一段行」。
不做单次 IS/OOS 切分 —— 那只给一个 OOS 数字，运气成分太大。

**④ 参数高原：不取排名第一，取邻域整体最好的。**
对网格上每个点，取其 ±1 格的邻居（macd 三维最多 26 个），要求
邻域内 OOS 收益的**中位数**为正、**标准差**低于阈值。
道理很直接 —— 真实存在的参数区域，邻居应该都还行；
过拟合的尖峰，邻居会掉下悬崖，而排名第一那组几乎必然是尖峰。

**⑤ 排序指标：超额收益 ÷ 最大回撤（或夏普），不是总收益。**
按总收益排会选出高杠杆高回撤的东西。另加硬门槛：
**完整轮次 ≥ 100**，否则样本不足直接淘汰。

**⑥ 标的池：含退市股**（C3）。流动性由 `min_turnover` 逐日判定，
不用 `status: listed` 静态过滤 —— 后者实测让收益虚高 23.66 个百分点。

#### ⚠ v0.3.4 的发现改变了这一版的输出形态

单次回测对单个决策的路径依赖极强（一笔拒单移动 7.5 个百分点，
且非单调，见 v0.3.4）。**结果库里存单点收益率是不够的** ——
海选必须输出邻域分布：中位数、四分位、以及「邻居里有几个是正的」。
一个只有自己好、邻居全差的点，应当排在一个整体温和向好的区域之后。

#### 开工前实测：噪声基线 19 个百分点

同一配置（`macd_full`）只把**初始资金改 ±0.1%**（100 万 ±1000 元）跑 5 次：
−29.66% / −46.50% / −27.55% / −31.39% / −27.85%，
**极差 18.95 个百分点，标准差 7.09**。

噪声随分散度骤降，且**非单调**：

| Sizer | 极差 | 标准差 |
|---|---|---|
| `slots=10` | 18.95 pp | 7.09 |
| `slots=30` | **27.08 pp** | 10.29 |
| `slots=100` | **4.48 pp** | **1.43** |

这个数改变了 v0.5 的形态，也**推翻了两个此前报过的结论**：
v0.3.4 的「含退市股 −23.66 个百分点」「流动性风控 −23.41 个百分点」
是 n=1 的单次对比，约合 3.3σ —— 方向大概率对（幸存者偏差抬高收益
是结构性的），但**那两个数字本身不可引用**。
同一段的流动性门槛敏感性扫描（0/50/100/200/300 完全相同、
500 → −7.5pp、1000 → −17pp、2000 → −5pp，非单调）**整段都在噪声里**。

#### 首次实跑的结论（2026-08-30）

216 组 × 18 窗 × (IS+OOS) + 450 次噪声探针 = **8,226 次回测，21 分 49 秒**
（12 并发，全历史 3,461 只 / 1,246 万行）。

```
1. 噪声基线      收益标准差 0.48 个百分点（90 组样本，每组 5 次 ±0.1%）
2. 全网格散布    2.22 个百分点  →  比值 4.61×  ✅ 参数确有影响
3. 稳健区域      没有一片满足「邻域中位数 > 0 且正的比例 ≥ 60%」
```

**结论：MACD 金叉在 A 股主板上不成立。** 不是「找到了最好的参数」——
分数最高的五组，OOS 中位数全是**负的**（−1.84% ~ −7.27%），
18 个独立窗口里赚钱的只有 39%~50%。

> 这正是这套方法要的东西：一个**可信的否定结论**。
> v0.3.4 之前，同一个策略在「按 ID 前 300 只」上跑出 +11.06%，
> 在「在市主板」上跑出 +31.92%，我们本来会拿着后者当事实。

顺带被这次实跑量出来的：噪声基线在 `slots ∈ {30,60,100}` 的网格上
只有 **0.48 个百分点**，远低于 `slots=10` 时的 7.09 ——
再次确认「海选必须站在足够分散的配置上」。

### v0.8 ✅ — 加密永续交易规则（插入项，2026-08-30）

**目标**：把 v0.3.3 留下的「交易规则层尚未实现」补上，
让加密市场真的能跑回测，且**跑出来的数字是对的**。

需求方定的三条：**加密固定逐仓 + 双向开仓持仓**、
**计价货币随市场不同**（加密 USDT 默认 1,000，A 股默认 20,000 元）、
**加密基准取 BTC 永续**。

#### 做了什么

- `CryptoMarket` —— 无涨跌停、T+0、按张申报、365 日年化、允许做空
- `MarginLedger` —— 逐仓 + 双向。强平**只吃掉该仓位的保证金**，不倒扣余额；
  同一标的多空各一个槽，独立记账、独立爆仓
- `NotionalCents` / `QtyForCents` / `MulDiv` —— 128 位中间量 + 逐标的
  `price_scale`/`qty_scale`/`ContractMult`
- `Market.Units()` 进接口 —— 计价与数量单位由市场回答，不按市场名查表
- 每市场默认值：初始资金、账本、市场规则、基准
- `trading.LegOf` —— 开平映射表**从四处各写一遍收敛成一处**

#### 这一版的教训：一张表写了四遍，四处都不报错

开平方向的映射（买+开=开多 / 卖+开=开空 / 买+平=平空 / 卖+平=平多）
原先散在保证金账本、轮次配对、仓位定方向、组合去重四个地方，
**逐个被发现** —— 每修好一个，下一个才暴露：

| # | 写错的表现 | 怎么发现的 |
|---|---|---|
| 1 | 记错槽位 | 写实现时想到的 |
| 2 | 空头轮盈亏符号相反、平空永不平 | 平均持有 190.8 天 × 314 轮 = 59,911 仓位·日，而 4 槽 × 2432 天只有 9,728 |
| 3 | **开空变成开多** | 数开平分布：`买开 170 / 卖开 0` —— 一笔空单都没有 |
| 4 | **开空信号被平多信号顶掉** | 修完 3 再数：`卖开 2`。还是几乎没有 |

第 4 处最隐蔽：`sigKey` 是 `(标的, 买卖方向)`，在单向市场里完全正确 ——
但双向下「卖」有两个意思，一多一空两棵镜像的树在同一根上
分别发出「平多（卖）」与「开空（卖）」，后者被去重掉了。

修完之后开平分布从 `168/167/0/166` 变成 `168/167/168/166`，
信号 336 → 669，收益 +146.07% → +129.64%
（在一个基准涨 982% 的市场里补上空头腿，本来就该亏钱）。

**验收**：
① 加密双向跑通 —— 669 笔成交、开平四向均衡、逐仓强平生效、
快照往返指纹逐位一致；
② **A 股三个基线指纹逐位不变** —— 这一版动了 sizer、组合去重、
轮次配对三处 A 股必经的代码，指纹不变才说明只加了新行为；
③ 服务端与命令行结果一致，A 股仍显示「元/股」、加密显示「USDT/张」。

细节与四处坑的完整记录见
[DESIGN-v0.8-crypto.md](DESIGN-v0.8-crypto.md)。 **量级 M**

#### v0.8.1 —— 风控、杠杆、持仓模式（同批）

- **回撤熔断**加`冷静期`与`触发时清仓`两项。冷静期期满
  **从当下权益重新起算回撤**；不重算的话，勾了清仓之后权益不再变动、
  历史峰值停在熔断之前，熔断会一到期就再次触发 ——
  实测「2021 年触发一次，之后 5 年 0 成交 285 次拒单」，
  而报告上只是一条平直的净值线。修后同一份配置触发 11 次、次次醒得过来
- **最低有效资金**（`min_capital`）：无持仓且开不起最小一手即判策略失败。
  判定同时挂在 `Check` 与 `OnStep` 上 —— 破产后 Sizer 根本不产生订单，
  只挂 `Check` 的话永远不会被调用
- **风控链进快照**（`StatefulRisk`）。冷静期是跨步状态，
  不存的话从快照恢复的那一步熔断静默解除
- **杠杆校验**：1–100；维持保证金率不得高于开仓保证金率；
  现货账本上设杠杆直接报错，不静默忽略
- **持仓模式**：装配器上的 仅做多 / 仅做空 / 双向持仓。
  后两者只在支持做空的市场出现，且**服务端也拦**（`ShortSeller` 接口）——
  不拦的话开空信号会被当成减仓丢掉，一笔不成交却什么都不报
- 组合里的规则树终于能在界面上编辑（从前渲染成一张空表）
- OKX 费率核对：taker 500ppm / maker 200ppm、最小张数与申报单位 0.01 张，
  与需求方给的数字逐项一致；新增 `Instrument.PriceTick`（`attrs.tick_sz`），
  并修掉撮合器拒单消息里写死的 `/1000`（在 BTC 上会印出大 10 万倍的数字）
