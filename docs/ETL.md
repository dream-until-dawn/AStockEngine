## 1. 数据流

```
       BaoStock ──┐
       新浪 ──────┤→ sources/ 适配器 ──→ 归一化形态 ──┐
   ingest/(其他语言) ┘   (Capability 声明能力)          │
                                                      ▼
                                          定点转换 + ts 计算 + 排序
                                                      │
                                                      ▼
                        data/bar/market=/freq=/year=/*.parquet
                        data/meta/*.parquet (+ *.csv 镜像)
                                                      │
                                                      ▼
                                          Go 引擎（只读，不写）
```

**Python 只负责把数据变成符合 [SCHEMA.md](SCHEMA.md) 的 Parquet，此外不做任何事。**
指标、信号、回测逻辑一律不在 ETL 层 —— 那是引擎的职责，放进来会破坏
C1（未来函数防护）与 C5（可复现性）。

## 2. 模块职责

| 文件 | 职责 |
|---|---|
| `etl/layout.py` | **目录布局的单一事实源**。`data/` 不进 git，布局必须由代码定义、可一键重建 |
| `etl/schema.py` | SCHEMA.md 的代码化：枚举、定点换算、pyarrow schema、标的属性推断 |
| `etl/sources/base.py` | 适配器接口 + `Capability` 能力位 |
| `etl/sources/baostock_src.py` | 个股日线 / 标的清单 / 交易日历 / 分红送配 |
| `etl/sources/sina_src.py` | ETF 日线 / 复权因子 |
| `etl/sources/external.py` | 非 Python 数据源的接入（见 [ingest/README.md](../ingest/README.md)） |
| `etl/build_instruments.py` | 构建 instruments + calendar（全量） |
| `etl/build_bars.py` | 构建 bar + adj_factor（抽试 / 全量），含质检 |
| `etl/sync_bars.py` | **bar 全量拉取与每日增量**，断点续跑、并发、自愈、逐年质检；含个股复权因子同步 |
| `etl/build_etf_factors.py` | **ETF 复权因子**重建 + 修正事件日 preclose |
| `etl/dump.py` | 查看 Parquet 内容，还原定点与枚举 |

## 3. 常用命令

> ⚠️ **必须用项目虚拟环境的解释器**，裸 `python` 会取到系统 Python
> （缺 baostock / akshare，且报错栈落在 `import pandas` 上，看不出真正原因）。
> 各入口脚本已内置 `etl/_venv_guard.py` 前置检查，用错解释器会直接提示正确命令。
>
> 下方以 PowerShell 写法为例；Bash 下把 `.\.venv\Scripts\python.exe`
> 换成 `./.venv/Scripts/python.exe`（Linux/macOS 为 `./.venv/bin/python`）。

```powershell
# 重建目录结构（data/ 不进 git，clone 后先跑这个）
.\.venv\Scripts\python.exe etl\layout.py

# 标的清单与交易日历（全量，约 2 分钟）
.\.venv\Scripts\python.exe etl\build_instruments.py

# 行情抽试：40 只个股（含 10 只已退市）+ 20 只 ETF
.\.venv\Scripts\python.exe etl\build_bars.py --stocks 40 --etfs 20 --start 2018-01-01

# --- 行情同步（全量 / 每日增量，同一个入口） ---
.\.venv\Scripts\python.exe etl\sync_bars.py --limit 8       # 试跑 8 只
.\.venv\Scripts\python.exe etl\sync_bars.py --workers 12    # 全量或增量（按状态自动判断）
.\.venv\Scripts\python.exe etl\sync_bars.py --status        # 查看进度
.\.venv\Scripts\python.exe etl\sync_bars.py --retry-failed  # 重试失败标的
.\.venv\Scripts\python.exe etl\sync_bars.py --compact       # 合并分片并去重
.\.venv\Scripts\python.exe etl\sync_bars.py --verify        # 逐年质检
.\.venv\Scripts\python.exe etl\sync_bars.py --only factors  # 只同步个股复权因子

# ETF 复权因子（个股走 sync_bars，ETF 无对应接口需重建）
.\.venv\Scripts\python.exe etl\build_etf_factors.py

# 查看数据
.\.venv\Scripts\python.exe etl\dump.py instruments --where "board==3" --limit 10
.\.venv\Scripts\python.exe etl\dump.py bar --symbol 600519 --limit 15
.\.venv\Scripts\python.exe etl\dump.py --schema bar
```

## 4. 数据源分工与理由

| 数据 | 来源 | 为什么是它 |
|---|---|---|
| 个股日线（含退市股） | BaoStock | 唯一同时给 `preclose` / `tradestatus` / `isST` 的免费源；停牌日照常返回行；无限流 |
| 标的清单、交易日历、分红 | BaoStock | 字段最全，`outDate` 语义统一（AkShare 的沪市名单给的是「暂停上市日期」，与「终止上市日期」不等价） |
| ETF 日线 | 新浪 | BaoStock 对 ETF 代码返回 0 行；新浪覆盖全历史 |
| 个股复权因子 | 新浪 | 事件式、16 位精度；实测还原后复权价误差 < 1e-6 |
| ETF 复权 | **暂无** | 🟡 未解决，见第 7 节 |

**东财已弃用**：约 10 次请求即触发 IP + 端点级封禁，实测 ≥45 分钟未恢复。
按此速率回补 1647 只 ETF 需 120 小时以上。

> 数据源不是一开始就选对的。v0.0 原计划「AkShare 单源」，实测后
> 主力源换成了 BaoStock，且 ETF 与个股走了不同的源 —— 这正是
> 约束 C9 把适配器当作核心设计而非可选预留的原因。

## 5. 关键设计决策

### 5.1 适配器返回「人类单位」，不返回定点整数

适配器只做**字段映射与语义归一**（列名、单位、枚举），
定点转换统一在 `build_*.py` 里做。

理由：定点换算依赖 `instruments.price_scale`，而适配器不应该知道标的元数据。
更重要的是，转换逻辑集中在一处才可能保证一致 ——
分散到每个适配器里，迟早出现某个源少乘一个 100。

### 5.2 价格以字符串在适配器内传递

BaoStock 返回的价格本就是字符串（`"1715.0000"`）。适配器**原样传递**，
由 `schema.to_fixed()` 用 `Decimal` 解析。

若中途转成 float 再转回，会引入二进制表示误差：
`2.675 * 100` 在 float 下是 `267.49999...`，直接取整得 267 而非 268。

### 5.3 `Capability` 能力位

没有任何一个免费源覆盖全部能力，因此调用方**必须先查能力**，
而不是靠捕获 `NotImplementedError` 来控制流程。

### 5.4 `instrument_id` 是整个数据集最脆弱的一环

按 `(market, symbol)` 首次出现分配、单调递增、**永不复用**。

`build_instruments.py` 每次运行前会自动备份 `instruments.parquet`
到 `data/meta/_backup/`。**这个备份不是可选的**：该文件一旦丢失，
所有 ID 重新分配，已有的全部 bar 分区文件随之失效，必须整体重建。

## 6. 踩过的坑

> 这一节是本文档存在的主要理由。以下每一条都是实测撞出来的，
> 不是设计时想到的。

### 6.1 涨跌停基准必须用 `preclose`，不能用 `close.shift(1)`

除权日的涨跌停基准是**除权调整后的前收盘价**。

```
比亚迪   2025-07-29（除权日）  前收 337.00  按前收算跌停 303.30  实际最低 109.77
宁德时代 2023-04-26（除权日）  前收 385.90  按前收算跌停 308.72  实际最低 210.01
```

大比例送转每年都有，不是边缘情况。→ 已固化为 [SCHEMA.md](SCHEMA.md) C8.1。

### 6.2 涨跌停价取整是**四舍五入**，不是银行家舍入 ⚠️

这条直接影响 v0.2 的 Market 模块。

```
4.35 × 1.10 = 4.785   numpy .round(2) → 4.78 ✗    实际涨停价 4.79
5.35 × 1.10 = 5.885   numpy .round(2) → 5.88 ✗    实际涨停价 5.89
```

numpy / pandas 的 `round()` 是**四舍六入五成双**（round-half-even），
而交易所是四舍五入（ROUND_HALF_UP）。在 `x.xx5` 上会差一分钱。

`build_bars.py: limit_price()` 用 `Decimal(..., ROUND_HALF_UP)` 实现，
**Go 侧实现涨跌停时必须遵循同一规则，不可用朴素浮点取整。**

### 6.3 低价股不能用「百分比」判涨跌停

0.24 元的票，涨停价 `0.24 × 1.2 = 0.288` 四舍五入为 **0.29**，
换算成百分比是 **+20.83%**，看着像超过了 20% 的限制，其实正是涨停价。

一分钱对低价股就是好几个百分点。**判涨跌停一律比价格，不比百分比。**

### 6.4 代码段推断规则会过期，必须实测校验

`build_instruments.py` 首次运行时质检报了两个未识别代码段：

| 代码段 | 实测最大日涨 | 结论 |
|---|---|---|
| `689009` 九号公司 | 17.84% | 科创板 CDR |
| `302132` 中航成飞 | 20.01%（13 天超 10.5%） | **创业板**，由创业板 300114 吸收合并后换段 |

若按「3 开头且非 300/301 即主板」推断，302 段会被判成 10% 涨跌停，
Broker 会在那 13 个交易日误判「涨停不能买」。

另外 `551xxx` 是 2025 年新启用的上交所科创债 ETF 代码段，
原交易所推断规则也未覆盖。

**教训**：代码段规则随时间变化，硬编码的推断迟早过期。
因此 `build_bars.py` 内置了**板块自洽校验** —— 用涨跌幅反向验证 `board`
与 `is_st` 标记，新代码段出现时会自动被捕获，不必等人发现。

### 6.5 不设涨跌幅限制的四种情形

板块自洽校验最初误报大量行，逐一排查后发现都是规则没建模：

1. **新股上市前 5 个交易日** —— 创业板 / 科创板一直如此；
   主板自 2023-04-10 全面注册制起同样适用。最初只排除了上市首日
2. **退市整理期首日** —— 无涨跌幅限制
3. **复牌首日** —— 2005-2007 股权分置改革期间尤为集中，对价送股造成的
   自然除权使复牌当日跌幅普遍在 -16% ~ -27%。
   实测：该区间 113 行越界中 **113 行**的前一交易日均为停牌，相关性 100%
4. **ST 的 5% 只适用于主板** —— 创业板 / 科创板的 ST 股仍是 20%

修正后 800,729 行 / 22 个年份 **0 项问题**。

### 6.6 涨跌幅规则有时间维度 ⚠️

**这是本项目至今最重要的一个发现，因为它是被数据自己挖出来的。**

逐年质检时，2026 年出现 22 行越界，全部是主板 ST / *ST 股，涨跌幅达到 10%
而非规则规定的 5%。而更早的数据里，同一批 ST 股严格守在 ±5% 内
（002214 大立科技 `is_st=1` 的 308 个交易日中有 306 天守 5%）。

越界全部集中在 **2026-07-06 之后**。查证确认：沪深北三大交易所新版交易规则
自 **2026 年 7 月 6 日**起实施，主板风险警示股票涨跌幅由 5% 放宽至 10%。

同类的还有：**创业板涨跌幅自 2020-08-24 起由 10% 放宽至 20%**。

结论：

- 涨跌幅限制**不是常量**，`build_bars.py: limit_ratio()` 按日期分段实现
- **v0.2 的 Market 模块必须同样按日期分段**，否则回测 2026-07-06 之前的
  ST 股会放行本该被拦截的成交
- 更普遍的教训：**规则会变，而写代码时的记忆会过期**。
  自洽校验的价值不在于发现数据错误，而在于发现**认知与现实的偏差** ——
  这条规则变更发生在编写者的知识截止之后，只能由数据揭示

### 6.11 corporate_action 与 adj_factor 的交叉核对

两张表来自**不同厂商**：因子取自新浪，分红送配取自 AkShare 的东财系汇编。
用「有因子事件却无分红记录」的数量做交叉核对，逐步逼出了三个问题：

| 缺口 | 成因 | 处置 |
|---|---|---|
| 7889 → 6818 | 只取了 `indicator="分红"`，**漏了配股** | 补抓 `indicator="配股"`，schema 扩 `rights_ratio` / `rights_price` |
| 丢失 117 行 | 同一除权日**既分红又配股**时，`drop_duplicates` 丢掉一条 | 改为按主键 `max` 聚合无损合并 |
| 剩余约 6770 | 1270 个落在 2005-2007 **股改对价送股**（不在分红/配股任一口径）；其余为厂商覆盖差异 | 记录为已知缺口，不强行补 |

> 交叉核对的价值不在于把缺口清零 —— 两个厂商的口径本就不可能完全一致 ——
> 而在于**每一类缺口都逼出一个具体原因**。前两类是真 bug，第三类是数据源固有差异。
> 若不做这个核对，配股会一直缺失，而 Portfolio 在配股除权日会直接对不上账。

### 6.10 因子正确性怎么验：看绝对误差，不看相对误差

抽 7 只个股用 `原始价 × 因子` 还原后与新浪后复权价比对，
**相对误差 1e-4 ~ 7e-4**，远大于 v0.0 时贵州茅台的 4.19e-07 —— 看着像有问题。

但换成绝对误差就清楚了：

```
优德精密  hfq均价 40.63   最大绝对误差 0.00495
中国建筑  hfq均价 12.94   最大绝对误差 0.00498
银轮股份  hfq均价 169.84  最大绝对误差 0.00499
迪生力    hfq均价  8.85   最大绝对误差 0.00496
```

**全部恰好卡在半分钱（0.005）以内** —— 这是四舍五入到 2 位小数的特征，
说明因子本身精确，误差全部来自新浪后复权价的显示精度。

茅台之所以相对误差看起来极小，只是因为它单价高（1400 元）：
同样的半分钱，除以 1400 就是 3.6e-6，除以 8.85 就是 5.6e-4。

**教训**：比对价格类数据时，相对误差会被价格水平放大或掩盖，
**先看绝对误差是否落在数据源的显示精度内**，再判断有没有真实偏差。

### 6.9 ETF 折算会伪装成暴跌 ⚠️

159527 广发中证云计算与大数据ETF：

```
2026-07-21  收盘 2.227
2026-07-22  开盘 0.720  收盘 0.747   -66.46%   成交量 6800万（平常 500-1600万）
```

这不是暴跌，是 **1:3 份额折算**。若不处理，引擎会认为持有该 ETF 一天亏 66%
—— 比原先记录的「分红未反映导致长期收益低估」严重得多。

**收口方案**（`etl/build_etf_factors.py`）：

| 环节 | 做法 | 可靠性 |
|---|---|---|
| 事件日期 | `fund_etf_dividend_sina`（非东财） | 权威 |
| 现金分红（金额已知） | `ratio = 前收 / (前收 - 分红)` | **精确** |
| 份额折算（比值 ≥1.5） | 由 `前收 / 开盘` 估算后**取整到常见比例** | 近似 + 取整 |
| 金额未知（比值 <1.5） | 直接用价格比值 | 近似，误差约为开盘跳空量级 |
| 分红 + 折算同日 | 先扣分红，残余比值仍达折算量级则叠加 | 组合 |

最终结果：**1047 行因子 / 271 只 ETF**（其余 1363 只无事件）。
仅 2 条告警（`159967` 3.6130、`159991` 2.7839），属按净值目标折算的
非整数比例，用原值并已标记。

**验证口径 —— 比较原始与后复权序列在事件日的跳变数**：

```
原始序列   事件日跳变 >15%：151 处   ← 假暴跌
后复权序列 事件日跳变 >15%：  0 处
```

#### ⚠️ 这个验证有盲区，后来被另一件事撞出来

上面的「0 处」只覆盖了**已经生成因子的 271 只 ETF**。
而**因子被静默跳过的 ETF 根本不在验证集里** —— 它们没有因子，
自然不会出现在「事件日跳变」的统计中。

盲区是在给 ETF 推断跟踪板块时暴露的：宽基 ETF 出现了不可能的涨跌幅 ——
`上证50ETF` 100%、`博时上证超大盘ETF` 944%。查下来是**份额折算有两个方向**，
而首版只处理了其一：

| 方向 | 价格 | 比值 `前收/开盘` | 例 |
|---|---|---|---|
| 拆分（份额增加） | 下跌 | > 1 | 159527 的 1:3 |
| **合并（份额减少）** | **上涨** | **< 1** | 510020 的 1:10、510100 的 1:2 |

首版的判断是 `raw < 1.001 即跳过`，把**全部合并事件**都当成「无实质调整」。
合并多发生在 ETF 净值跌得过低时（510020 折算前仅 0.174 元）。

修正后 510020 的因子为 0.1，后复权序列 `0.1740 → 0.1818 → 0.1833` 连续。

**教训**：验证集是由被验证对象自己产生的时，就会有这种盲区 ——
「没生成因子」和「因子正确」在这个口径下无法区分。
后续的验证改为**遍历全部有事件的 ETF**，而不只是有因子的那些。

为什么必须取整：159527 由价格推出的比值是 **3.0931**，而深交所份额数据显示
`(168,100,450 - 4,000,000) × 3 = 492,301,350`，真实比例是 **3.0** ——
价格估计偏离 3.1%，直接用会留下 3% 的永久性水平偏移。

**为什么事件日期是关键**：同样是 -66%，落在事件日就是折算，不在事件日就是真跌。
没有权威的事件日期，任何纯价格启发式都可能把暴跌误判为折算，反之亦然。

#### 这块连改了三次，三次都是同一类错误

| # | 我以为的 | 数据的真实语义 | 怎么发现的 |
|---|---|---|---|
| 1 | 「累计分红 = 0」= 没有分红 | = **金额未知**（数据源早期缺金额） | 1.11 / 1.10 这类比值太小，折算不可能是 1.1 倍 |
| 2 | `preclose /= ratio` 可重复执行 | **不幂等**，重跑会二次缩小 | 准备重跑时意识到，连跑两次做对照 |
| 3 | 分红与折算互斥 | **可同日发生**（159922 2024-12-02） | 事件日跳变计数还剩 1 处不肯归零 |

三个都是**把「我以为的数据语义」当成了「数据的真实语义」**。
能抓出来靠的是同一件事：**用数据自己验数据**（事件日跳变计数、幂等性对比、
后复权连续性），而不是看代码有没有报错 —— 这三处代码全程没有抛过异常。

同样的方法此前还抓出了 ST 涨跌幅规则变更、302 代码段归属、涨跌停取整方式。

验证（159527）：

```
交易日      原始收盘  因子   后复权收盘
2026-07-21   2.227   1.0     2.227
2026-07-22   0.747   3.0     2.241     ← 序列连续，假暴跌消除
2026-07-23   0.728   3.0     2.184
```

### 6.7 停牌行的形态

BaoStock 停牌日照常返回行（这是它优于东财之处）：

```
date        open   high   low   close  preclose  volume  amount  turn  tradestatus
2019-04-26  1.0400 1.0400 1.0400 1.0400  1.0400      0   0.0000  (空)      0
```

- OHLC 全等于停牌前收盘价 → 价格序列连续，指标计算不会出现空洞，**无需回填**
- ⚠️ `turn` 是**空字符串**而非 `0`，直接 `float("")` 会抛异常

因此 `schema.to_fixed()` 对 `None` / `""` / `NaN` / `inf` 一律返回 0 ——
让转换函数兜底，好过在每个调用点各写一遍防御。

### 6.8 bar 表天然具备 point-in-time 语义

因为停牌日也有行，所以：

```
某日标的池 = SELECT DISTINCT instrument_id FROM bar WHERE trading_day = d
```

上市前无行、退市后无行、停牌有行且 `tradestatus=0`。
**因此不需要单独的 point-in-time 宇宙表** —— 若按每日快照存，
7200 × 8000 天 ≈ 5760 万行，比 bar 表还大。

## 9. 新增数据源

- **Python 源**：在 `etl/sources/` 下实现 `DataSource` 子类，声明 `capabilities`
- **其他语言的源**：放 `ingest/<source>-<lang>/`，见 [ingest/README.md](../ingest/README.md)

两种情况下 DataGateway 以上的代码都不应改动（约束 C9）。
