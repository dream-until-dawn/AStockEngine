# 数据核对台（Web）

> 前端 React + Vite，后端 `engine/cmd/server`。
> 最后更新：2026-08-29（v0.3.1 加入回测结果视图）

## 它是什么

**一个用来回答「数据准不准」的工具，不是回测服务。**

ETL 产出的四张非行情表、17,670,265 行日线、以及引擎算出的技术指标，
在这里被摆到同一个页面上，用来肉眼核对与交叉比对。

因此有一条贯穿全篇的原则：

> **凡是引擎能算的，一律走引擎，不在服务端另写一份实现。**

前端一行指标都不算。自己再算一遍等于新增一条实现路径，
两条对不上时反而分不清谁错了 —— 而这个页面存在的意义正是判断谁对。

## 跑起来

后端（首次启动约 30 秒，见下节）：

```bash
cd engine && go run ./cmd/server
```

前端开发模式（热更新，把 `/api` 代理到 8123）：

```bash
cd web && npm install && npm run dev
```

打开 http://localhost:5173 。

也可以只跑一个进程：`cd web && npm run build` 之后，
Go 服务会直接伺服 `web/dist`，访问 http://127.0.0.1:8123 即可。

常用参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `-addr` | `127.0.0.1:8123` | 监听地址，只绑本机 |
| `-data` | `../data` | 数据根目录 |
| `-fee` | `../configs/fee/ashare_default.json` | 费率配置 |
| `-web` | `../web/dist` | 前端产物；不存在则只提供 API |

## 六个视图

| 视图 | 回答什么问题 |
|---|---|
| 概览 | 各表行数、覆盖区间、磁盘与内存占用 |
| **回测** | 跑一次策略，看净值 / 基准 / 回撤 / 逐轮交易 / 拒单归因 |
| 标的列表 | 筛市场 / 板块 / 类型；**反查缺口**（哪些标的没有行情 / 没有因子） |
| K 线 | 单标的的价与指标，三种复权可切；可展开该标的的因子表、分红送配表与**两表对账** |
| 交易日历 | 含休市日；周末却开市之类的异常会被标出来 |
| 复权因子 / 分红送配 | 两张表**互相对账**，缺一边的标「缺」 |

标的列表里有个容易被忽略但很有用的过滤器：**某日在市**。
填 `20190101` 就只留当天在市的标的 —— 回测 2019 年时用的应当是这份名单，
而不是今天的。这是核对 C3（幸存者偏差）最直接的工具。

## 设计决策

### 1. 全量常驻内存，不做按需加载

启动时把 22 个年份分区一次性载入：**1.25 GB / 约 30 秒**。

这不是偷懒。`mktdata.Load` 无论过不过滤都要把全部分区**整个读一遍** ——
实测取单只标的（4,039 行）耗时 28.7 秒，取全市场（17,670,265 行）耗时 30.1 秒。
「按需加载」在这里比全量还慢。

分区文件每个只有 2 个行组、且未声明排序列，所以行组裁剪也帮不上忙。

载入后不再变更，故所有读取无需加锁。**数据更新的方式是重启服务**，
这与 ETL 的批式产出节奏一致。

> 代价是改后端代码后要等 30 秒才能验证。开发前端时不受影响 ——
> Vite 有热更新，后端进程一直开着即可。

### 2. K 线的指标由**真引擎**算出

不是「读数据再算指标」，而是真的装配一个 `engine.Engine`：

```
Columns.Subset(单标的)  →  eng.New(..., probeStrategy, ...)  →  RunAll()
```

`probeStrategy` 只观察不下单，每步把 `ctx.Indicator(id, key).Values()` 抄下来。
走的是与回测**逐字节相同**的代码路径：同样的 `AdjustBar`、同样的 `Update` 顺序。

`Columns.Subset` 就是为此加的：从已载入的全量列式表切出单标的是纯内存操作，
而走 `Load` 要 30 秒。它返回的是另一个 `*Columns` 而非底层切片，
所以 C1 的结构性保证（包外拿不到数组）依旧成立。

### 3. 引擎跑全程，只裁剪输出

指标是增量的。若从用户选的 `from` 起步，那天的 MACD 处于冷启动状态，
与真实回测（跑完整历史）算出的值**不同**。照那样返回，
这个工具就会在它唯一要回答的问题上给出错误答案。

所以引擎总是从有数据的第一天跑起，只把 `from` 之前的行丢掉。
接口会返回 `engine.warmupBars` —— 少了这个数字就无法判断区间首日的指标是否可信。

### 4. 复权模式同时作用于 K 线与指标

第一版把两者拆成两个选择器：K 线用不复权、指标用后复权（回测默认）。
结果是均线画在 140–240，K 线画在 9 附近，**主图完全不可读**。

现在一个开关管到底。两者必须同基准，这不是取舍问题。

### 5. 但同时给出回测基准下的值

展示基准由用户选（要跟同花顺这类软件对得上），而**回测固定用后复权**
（序列必须连续，否则除权日产生假信号）。两者不同时，同一根 bar 就有两组指标值。

与其挑一组显示，不如两组都给：接口跑两遍引擎，
`ind` 是所选基准、`indBt` 是回测基准，读数面板并排摆着。
「我看到的」与「引擎回测时看到的」差多少，一眼可见。

单标的的引擎跑一遍是毫秒级，跑两遍不构成问题。

### 6. 前复权能算，但只在展示路径上

前复权锚定末日，每来一次新除权就改写全部历史 ——
用于决策即构成未来函数（C1）且不可复现（C5）。

引擎的 `StepContext.AdjClose` **根本不提供** `AdjQFQ`，这是结构性的拒绝。
K 线页能显示前复权，是因为服务端在引擎之外调 `Adjuster.Adjust` ——
展示路径与决策路径由此保持分离。

### 7. 线上传整数

价格、金额、因子一律以**定点整数**下发，前端按 `/api/meta` 给的 scale 换算。

传浮点会在传输层就损失精度，而「数据准不准」正是这个工具要回答的问题。
读数面板同时显示「元」与原始整数：前者用来跟行情软件比，后者用来跟 Parquet 原值比。

## 接口

所有接口都在 `/api` 下，返回 JSON。`{id}` 可以是 `instrument_id`，也可以是代码（如 `600000`）。

| 接口 | 说明 |
|---|---|
| `GET /api/meta` | 枚举字典、定点 scale、数据统计、当前范围 |
| `GET /api/instruments` | 标的列表，筛选 + 排序 + 分页 |
| `GET /api/instruments/{id}` | 单标的详情 + 因子事件 + 公司行动 + **两表对账** |
| `GET /api/calendar` | 交易日历 |
| `GET /api/factors` | 全市场复权因子事件 |
| `GET /api/corp-actions` | 全市场分红送配 |
| `GET /api/configs` | 列出回测配置（含解析结果，供前端改参数后 POST 回来） |
| `POST /api/backtest` | 跑一次回测，返回绩效 / 净值 / 成交 / 拒单 / 逐轮 |
| `POST /api/universe` | 预览标的池：命中多少只、都是些什么 |
| `GET /api/kline/{id}` | K 线 + 引擎算出的指标 |

`/api/instruments` 的过滤参数：

```
?q=          代码或名称子串
&market= &exchange= &type= &board= &trackedBoard= &status=      逗号分隔多选
&hasBars= &hasFactor= &hasCorp=                                 1=有 0=无
&listedOn=YYYYMMDD                                              point-in-time
&sort= &order=asc|desc &page= &pageSize=
```

`/api/kline/{id}` 的参数：

```
?adj=none|qfq|hfq        复权模式，K 线与指标同基准（默认 none）
&from= &to=              交易日区间；引擎仍跑全程，只裁剪输出
&ma=5,10,20,60           主图均线周期
&macd=12,26,9 &kdj=9,3,3 副图参数
```

响应里每根 bar 的 `ind` 是所选基准下的指标，`indBt` 是回测基准（后复权）下的同一批；
`adj=hfq` 时两者相同，`indBt` 省略。`ready` / `readyBt` 标记预热是否完成 ——
**预热期内的值是垃圾**，前端不画也不显示成数字。

## 回测结果视图（v0.3.1）

**范围是刻意收窄的：只看跑完的结果，不做单步。** 会话管理、WebSocket 事件流、
快照远程恢复都留给 v0.4 —— 但两者**共用同一套视图**，
现在做的不是丢弃品，它就是 v1.0 单步界面减掉驱动那一层。

### 回测在服务端跑

这是 v0.3 那句设计注释的兑现：`Config.Assemble(ds)` 当初就是按
「多次装配共用一份数据」写的（原话：海选要跑几百组配置，数据只该载入一次）。
数据已经在内存里，于是一次回测只要 **~200 毫秒**，
浏览器里点一下就出结果，而不是每次等 30 秒重读盘。

两个必要的约束：

- **标的池上限 3000 只。** `Assemble` 要把全量列式数据 Subset 成子集，
  那是一次拷贝。285 只约 30 MB 无所谓，全市场 7,175 只就是又一个 1.25 GB。
  超限直接报错并建议改用命令行，而不是把服务端撑爆。
- **强制指向服务端已载入的那份数据。** 从浏览器传来的配置里 `data.root`
  可能指向别处，而服务端手里只有启动时载入的这一份。

拒单在步进循环里收集，而不是把记录级别提到 `full` ——
`full` 会把每步的信号也留下来，`buy_and_hold` 有 41 万条信号，那是白吃内存。

### 成交叠在 K 线上

**这是「实感」的来源。** 信号、指标、成交摆在同一张图上，
才看得出交易发生时图上是什么样：MACD 金叉 → 红色买入箭头，死叉 → 绿色卖出箭头，
副图里的交叉点就在正下方。

实现上不需要后端配合：回测结果存在前端的模块级 store 里，
K 线页读它筛出本标的的成交。代价是刷新页面就没了 —— 可以接受，重跑只要 200 毫秒。

一个踩过的坑：**只画区间内的成交**。区间外的标记不会被丢掉，
而是被挤到图的右边缘堆成一摞 —— 看起来像最后几天疯狂交易，
实际是 2020 年的单子跑到 2026 年的位置上去了。

### 标的池选择器

按市场 / 类型 / 板块 / 交易所 / 状态筛，也能直接指定几只代码
（**填了代码就忽略其余条件** —— 「就在这几只上跑」是最直接的意图，
不该再被板块类型二次过滤掉）。

选择器**不自己算命中了哪些标的**，而是把规格 POST 给 `/api/universe`，
那边走的是与真跑**完全相同**的 `ResolveUniverse`。
预览说 3,193 只、真跑却是别的数，那种不一致比没有预览更糟。

配置的原始 JSON 是唯一真相，选择器只是它的一个视图：
读出 `data.universe` 给选择器，选完写回去。两边各存一份状态必然会不同步。

**这一块的价值被一次实测坐实了**：同一个 `macd_cross`，
在原来的「按 ID 前 300 只」上跑输基准 15.25 个点，
换成「在市主板全部个股」（3,193 只）就跑赢 5.61 个点。
换池子换的是**结论**，不是精度。原来那 300 只实际是上交所主板按代码排前 300，
行业集中在钢铁石化基建，还混着只有 314 根 bar 的短命标的。

### 大标的池：上限、缓存与内存

- **上限 6,000 只。** 装配要把全量列式数据裁成子集，那是一次拷贝：
  285 只约 30 MB，3,193 只约 550 MB，全部 7,200 只就是又一个 1.25 GB。
  6,000 让「全部个股」（5,549）能跑、「所有标的一起回测」被挡住 ——
  后者不是一个有意义的池子。命令行没有这个限制（只载入所需标的，压根不用裁）。
- **子集缓存一份。** 调策略参数时会反复跑同一个池子，
  slots 从 10 改到 5 再跑没有理由再拷贝 550 MB。只缓存最近一次，不做 LRU。
- **跑完主动还内存。** 大池子跑完调 `debug.FreeOSMemory()` ——
  Go 的 GC 不会主动还给操作系统，本地工具没必要攥着。
  实测：载入后 3.3 GB → 跑完 1.7 GB。

> 踩过的坑：加了子集缓存之后，**基准区块整个消失了**。
> 因为基准不在标的池里，而缓存把 `ds.Columns` 换成了裁好的子集，
> 再去取基准就取不到了。修法是在裁之前就把基准序列算好存进 DataSet。
> 这类失败是静悄悄的 —— 不报错，报告里只是少了一段。

### 基准曲线归一化到初始资金

两条线画在同一根坐标轴上，单看策略 +11% 觉得还行，
跟基准摆一起才知道跑输了 15 个点。

**覆盖不到的日子留空而不是补值** —— 拉一条直线过去会让人以为
那段基准没涨没跌，而事实是那段根本没有数据（宽基 ETF 最早到 2012）。

### 「本次回测未计入」面板

回测结果里多了一块 `disclosures`，与绩效同屏显示。

**为什么值得占一块面板**：报告上的每个数字都在说「发生了什么」，
**没有任何一处在说「什么没算」**。漏算的成本不报错、不异常，
只是让结果一致地偏乐观 —— 这是本项目里最难发现的一类错。
v0.3 的滑点就是这样藏了很久：它混在成交价里，报告只看得到佣金与
印花税，直到单列出来才发现 `macd_cross` 的滑点是 8.89 万元
（占初始 8.89%），与全部费用同一量级。

当前会出现的条目：

| 条件 | 提示 |
|---|---|
| 标的池含永续合约 | 资金费率未计入（实测 BTC 年化约 4.4%，做多为主的结果偏乐观） |
| 恒有 | 未建模集合竞价（开盘价取 09:30，不含 09:25 竞价撮合） |
| 恒有 | 未建模融资融券与个股期权（现货多头账本，不支持做空与杠杆） |

由 `Config.Disclosures()` 生成，CLI 报告印同样一段。
**列表恒不为空** —— 「本次回测把一切都算进去了」这句话永远是假的。

## 已知边界

- 只读。这里不改数据，也不触发 ETL。
- 单机单进程，无鉴权，默认只绑 `127.0.0.1`。
- 重启才能看到新数据。
- 一次请求返回整段区间的 bar（20 年约 2 MB JSON）。本机用没问题，不适合放到公网。
- 加密标的能看 K 线与指标，但**跑不了回测** —— 交易规则（T+0、无涨跌停、
  资金费率计费）尚未实现，`checkMarketRules` 会直接拒绝而不是套 A 股规则。
