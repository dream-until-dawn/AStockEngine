## 0. 先说结论：这一版真正要解决的不是「跑得快」

开工前实测了一件事，结果推翻了 v0.5 原本的形态。

**实验**：同一个配置（`macd_full`，3,376 只主板个股含退市，2020 起），
只把**初始资金改动 ±0.1%**（100 万元 ±1000 元），跑 5 次。

初始资金差 1000 元，经济上可忽略；但它改变每一单的取整，
进而改变哪些单能成交、成交多少 —— 路径就此分叉。

| 初始资金 | 总收益 | 成交 | 轮次 | 最大回撤 |
|---|---|---|---|---|
| 1,000,000 | −29.66% | 1,424 | 709 | 55.71% |
| 1,001,000 | **−46.50%** | 1,436 | 715 | 61.68% |
| 999,000 | −27.55% | 1,495 | 744 | 49.03% |
| 1,000,500 | −31.39% | 1,490 | 742 | 50.00% |
| 999,500 | **−27.85%** | 1,560 | 777 | 43.10% |

**收益极差 18.95 个百分点，标准差 7.09；回撤极差 18.58 个百分点。**

这就是**噪声基线**：同一个策略、同一段行情、同一套参数，
仅仅因为一个经济上无意义的扰动，结果就能差 19 个点。

### 由此推翻的三件事

**① 单点收益率不是一个可比较的量。**
海选如果输出「参数组 A 收益 +12%，参数组 B 收益 +5%，选 A」，
那 7 个点的差距**完全在噪声之内**，这个排名是随机的。

**② 我此前报过的两个数要降级。**
v0.3.4 里我报了「含退市股 −23.66 个百分点」「流动性风控 −23.41 个百分点」。
那是 **n=1 的单次对比**，而噪声标准差是 7.09 —— 23.66 约合 3.3σ，
方向大概率是对的（幸存者偏差抬高收益是结构性的，不只是实测的），
但**「23.66」这个数字本身不可引用**。同一段的门槛敏感性扫描
（0/50/100/200/300 完全相同、500 → −7.5pp、1000 → −17pp、2000 → −5pp，
非单调）现在看**整段都在噪声里**。

**③ 「量级 L」的重点从并发挪到了统计。**
计算早就不是瓶颈（v0.3.4 实测：内存边际 2.7 MB/worker，
全历史一次回测 8.1 s）。真正难的是**从噪声里把信号捞出来**。

### 噪声从哪来，怎么压

噪声的根源是**集中度**：`slots=10` 时，3,376 只标的里持哪 10 只近乎任意，
一次不同的成交就会级联改变后面所有的持仓。实测：

| Sizer | 5 次的收益 | 极差 | 标准差 | 成交数极差 |
|---|---|---|---|---|
| `slots=10` | −29.7 −46.5 −27.6 −31.4 −27.9 | 18.95 pp | 7.09 | 136 |
| `slots=30` | −18.7 −35.7 −31.5 −45.8 −19.1 | **27.08 pp** | 10.29 | 568 |
| `slots=100` | −26.8 −29.0 −29.4 −31.3 −29.3 | **4.48 pp** | **1.43** | 325 |

**分散到 100 只，噪声降到 1/5。** 但**不是单调的** ——
`slots=30` 反而比 `slots=10` 更差。猜测与最小申报单位有关
（100 万 ÷ 30 ≈ 3.3 万元/仓，在高价股上取整到 100 股的相对误差很大），
**但这只是猜测，需要单独验证**，不写进结论。

> 这条本身就是 v0.5 的一个产出：**海选必须先确认自己站在一个
> 噪声足够低的配置上**，否则测的是随机数不是策略。

## 1. 设计原则

从上面直接推出四条：

1. **一切结论以分布出现，不以单点出现。** 每个参数组的结果是
   18 个 OOS 窗口的分布（中位数 / 四分位 / 正的比例），不是一个数。
2. **噪声基线与结果同屏。** 报告上任何一个差异，旁边必须有
   「本次配置的噪声基线是多少」。差异小于基线的，明确标注「不可分辨」。
3. **选区域不选尖峰。** 邻域整体好 > 自己最好。理由不再只是
   「防过拟合」这种教条 —— 实测表明排名第一那组的领先量本来就在噪声里。
4. **每一行结果都能一键重跑。** 存输入/输出指纹（C5 已就绪）。

## 2. 工作单元与并发

### 2.1 一次海选的结构

```
sweep = 参数网格（M 组） × Walk-Forward 窗口（18 个） × 阶段（IS / OOS）
```

M=300 时是 300 × 18 = **5,400 次回测**。按实测每个 4 年窗口
**1.147 s**（975 步 / 260 万行 / 2,922 只），
单线程 ≈ 103 分钟，8 worker ≈ **13 分钟**。

### 2.2 按窗口分批，不按参数组分批

```
for 每个窗口 w:                 ← 串行
    裁一次子集（该窗口的日期区间）
    for 每组参数 p:             ← 并发，共享上面那一份子集
        跑 IS，跑 OOS，写一行结果
```

**顺序不能反。** 反过来（参数组在外、窗口在内）会让每个 worker
各自持有一份不同区间的子集 —— v0.3.4 实测每份 358 MB，
8 个 worker 就是 2.8 GB，而共享只读内存的优势正是这一版的前提。

窗口串行的代价是 18 次 `Subset`，摊到 300 组参数上可忽略。

> `Assemble` 里的 `narrow` 判据在 v0.3.4 已放宽成子集关系，
> 预裁一次之后各 worker 拿到的是同一个指针，不会再拷。
> 服务端 `narrowCached` 是同一形态，BatchDriver 照抄。

### 2.3 预热前缀与 `TradeFrom`

窗口切开后，每段开头的指标是**未预热**的 —— MACD(26) 要 26 根 bar
才就绪。不处理的话每个窗口的头一个月被系统性地削掉信号，
而这个削法在 18 个窗口上是一致的偏差，不是噪声。

方案：**子集多裁一段预热前缀，引擎在 `TradeFrom` 之前只喂指标不交易**。

```
Subset(ids, isFrom − warmupDays, oosTo)     ← 数据多给一段
engine.Config.TradeFrom = isFrom            ← 这天之前不下单
```

引擎侧改动很小：`Step()` 的第 6–8 步（策略 / Sizer / Risk）
在 `tp.TradingDay < TradeFrom` 时跳过，第 2–5 步（指标、公司行动、
撮合、重估）照常。撮合照常是必须的 —— 预热期不下单，
也就没有在途单，跳过反而要加分支。

`warmupDays` 由配置给，默认取网格里最长的指标周期 × 3。

> **不选「游标带区间」的方案**：那要给 `Cursor` 加 `Seek` 与 `stop`，
> 并把每个标的的行指针二分定位到区间起点。能省下 18 次 Subset 的内存，
> 但那 18 次本来就是串行的、峰值只有一份。为省一个不成为瓶颈的东西
> 去动最热的那段代码，不划算。

## 3. 参数网格

### 3.1 配置形态

新目录 `configs/sweep/`，一份 JSON 描述一次海选：

```json
{
  "name": "macd 粗网格 · 主板含退市",
  "base": "../backtest/macd_full.json",
  "grid": {
    "strategy.params.short":  [5, 8, 12, 16, 20],
    "strategy.params.long":   [20, 26, 34, 45, 60],
    "strategy.params.signal": [5, 9, 14],
    "sizer.params.slots":     [30, 60, 100]
  },
  "constraints": ["strategy.params.short < strategy.params.long"],
  "walk_forward": { "is_years": 3, "oos_years": 1, "step_years": 1, "warmup_days": 90 },
  "noise_probe": { "points": 5, "repeats": 5, "perturb_pct": 0.1 },
  "gate":  { "min_round_trips": 100 },
  "rank":  "excess_over_maxdd"
}
```

**`grid` 用点号路径写进 base 配置。** 值是**显式列表**，不是
`[min, max, step]` —— 这是 v0.3.4 的拍板：`macd_cross` 的合法空间有
670 万组，全撒一定能找出一组「历史上完美」的参数，而它一文不值。
先跑一个可辩护的粗网格，**发现高原后再在高原附近加密**。

上面这份：5 × 5 × 3 × 3 = 225 组，`short < long` 过滤后 **180 组**，
× 18 窗 = 3,240 次回测 ≈ 8 worker 8 分钟。

> 也支持 `{"from":5,"to":20,"step":3}` 的糖，但**文档默认写显式列表** ——
> 糖会让人不自觉地把范围拉满。

### 3.2 展开与校验

- 笛卡尔积 → 按 `constraints` 过滤 → 每组过一遍 `dryBuild`
  （v0.3 已有：把每个模块真构造一遍），**跑之前就报错**，
  而不是跑到第 137 组才发现参数名拼错
- 参数组按**规范化 JSON 的指纹**编号，同一组参数在两次海选里编号一致
- 展开后先打印规模与预估耗时，**超过阈值要确认** ——
  「我以为是 300 组结果是 30,000 组」这种事应当在开跑前发现

## 4. Walk-Forward

全量 5,260 个交易日（2005-01-04 ~ 2026-08-28，21.65 年），
IS 3 年 / OOS 1 年 / 步进 1 年 → **18 个窗口**。

```
窗口 0:  IS 2005-2008   OOS 2008-2009
窗口 1:  IS 2006-2009   OOS 2009-2010
...
窗口 17: IS 2022-2025   OOS 2025-2026
```

**不做单次 IS/OOS 切分** —— 那只给一个 OOS 数字，
而我们已经知道单个数字的不确定性有 19 个点。18 段才谈得上分布。

IS 的用途**不是选参数**（那会引入选择偏差），而是：

- 确认这组参数在 IS 上**根本不能用**时直接淘汰（省 OOS 的算力）
- 对比 IS / OOS 的落差，落差极大的是过拟合的直接证据

真正的评分**只用 OOS**。

## 5. 噪声基线

### 5.1 怎么测

不对每一组参数都测（那是 5 倍开销）。取 `noise_probe.points` 个
**代表点**（网格的中心 + 四角），每个点跑 `repeats` 次，
每次把 `portfolio.initial_cash_cents` 扰动 ±`perturb_pct`%。

代价：5 点 × 5 次 × 18 窗 = 450 次回测 ≈ 全量的 14%，**可接受**。

### 5.2 为什么用初始资金做扰动

要的是「经济上无意义、但会改变执行路径」的扰动。候选与取舍：

| 扰动 | 为什么不用 / 用 |
|---|---|
| 随机种子 | **引擎里没有随机数**（C5），无从扰动 |
| 起始日 ±3 天 | 会改变样本区间，那是真的差异不是噪声 |
| 滑点 ±0.01bp | 改的是成本模型，属于「参数」而不是「噪声」 |
| **初始资金 ±0.1%** | ✅ 不改变任何规则与样本，只改每一单的取整 |

### 5.3 报告里怎么用

```
噪声基线（5 点 × 5 次）：OOS 收益标准差 1.43 pp（slots=100）
参数组 A 与 B 的 OOS 中位数差 0.9 pp  →  ⚠ 小于噪声基线，不可分辨
参数组 A 与 C 的 OOS 中位数差 8.2 pp  →  可分辨（5.7σ）
```

**「不可分辨」必须印出来**，而不是让排名默默地把它变成「A 比 B 好」。

## 6. 高原判定

### 6.1 邻域

网格是一个 k 维格点集。某点的邻域 = 每维 ±1 格的全部组合
（macd 三维最多 26 个邻居，加上自己 27 个）。
边界点的邻居少，**邻居数要一起报** —— 3 个邻居的「高原」不算高原。

### 6.2 判据

对每个格点，在其邻域上算 **OOS 收益的分布**（18 窗 × 邻居数个样本）：

| 量 | 判据 | 为什么 |
|---|---|---|
| 中位数 | > 0 | 用中位数不用均值：一个邻居暴涨不该救活一个区域 |
| 正的比例 | ≥ 60% | 「多数窗口多数邻居赚钱」比「平均赚钱」硬 |
| 四分位距 | 与噪声基线比 | **IQR ≈ 噪声基线 ⇒ 这个区域是平的**（好事）；IQR ≫ 基线 ⇒ 邻居之间有真实差异，不是高原 |
| 邻居数 | ≥ 6 | 边界点排除 |

**最后按邻域中位数的 `超额 ÷ 最大回撤` 排序**，不是按总收益 ——
按总收益排会选出高杠杆高回撤的东西。
硬门槛 **完整轮次 ≥ 100**，样本不足直接淘汰。

### 6.3 一个必须防的自欺

如果**整个网格的散布都 ≈ 噪声基线**，那说明这些参数**根本不影响结果**，
此时「找到了一个高原」是幻觉 —— 整张网格都是同一片平地。
报告要先回答这个问题：

```
全网格 OOS 中位数的散布 3.1 pp  vs  噪声基线 1.4 pp
→ 参数确实有影响（2.2×），可以谈高原
```

散布 / 基线 < 1.5 时，直接给结论「**该参数在此区间内无可辨别的影响**」，
不出高原排名。

## 7. 结果存储

### 7.1 Parquet，不引 DuckDB

ROADMAP 原文写的是「结果库（DuckDB）+ 查询」。建议**只用 Parquet**：

- SCHEMA.md 第 7 节本来就把 `results` / `equity` 规划为 Parquet 表
- 规模很小：5,400 行 × 约 30 列，**不到 2 MB**。10 万次也就 40 MB
- Go 侧引 DuckDB 要 **cgo**（`go-duckdb` 是静态链接的 C 库），
  会打破当前纯 Go 的构建与交叉编译，为一个「查 5,400 行」的需求
  背上永久成本
- 查询在 Go 里全量载入内存做即可 —— 过滤、排序、分组，都是几毫秒

> DuckDB 仍然可以用，但用在**引擎之外**：Python 侧要做临时分析时
> `duckdb.sql("select * from 'data/results/*.parquet'")` 一行就能读，
> 这正是选 Parquet 的好处 —— 不绑定查询引擎。

### 7.2 表结构

`data/results/sweep={sweep_id}/part-*.parquet`，一行一次回测：

| 字段 | 类型 | 说明 |
|---|---|---|
| `sweep_id` | STRING | 本次海选标识（配置指纹前 12 位） |
| `param_id` | INT32 | 本次海选内的序号，按规范化参数 JSON 定序 |
| `param_fp` | STRING | 参数指纹，**跨海选稳定**。两个都存：序号紧凑可排序，指纹才是身份 |
| `params` | STRING | 该组参数的 JSON |
| `window` | INT16 | 窗口编号；−1 表示整段 |
| `phase` | INT8 | 0=IS 1=OOS |
| `probe` | INT8 | 0=正式；≥1=噪声探针 |
| `from_day` / `to_day` | INT32 | 实际区间 |
| `total_return` / `excess_return` / `max_drawdown` / `sharpe` / `annual_vol` | DOUBLE | 绩效 |
| `fills` / `round_trips` / `win_rate` | INT32 / DOUBLE | 样本量与胜率 |
| `fee_cents` / `slippage_cents` / `turnover` | INT64 / DOUBLE | 摩擦 |
| `bench_covered` / `bench_total` | INT32 | 基准覆盖了多少个时点，**必须存**（见下） |
| `input_fp` / `output_fp` | STRING | **C5：任何一行都能一键重跑** |
| `elapsed_ms` | INT32 | |
| `err` | STRING | 非空表示这次跑失败。**失败的行也留着** —— 「这组参数在这个窗口跑不了」本身是发现 |

> **绩效列用 float64 而不是定点。** 与 SCHEMA 0.2 的「比率用 ppm」不同，
> 理由是这些是**输出**，永远不会再喂回引擎。C5 由指纹保证，
> 不由指标的编码方式保证。定点在这里只会让读表的人多做一次除法。

> **`bench_covered` 是实现时才发现必须存的。** 宽基 ETF 最早 2012 年
> （510300 从 2012-05-28 起），而 Walk-Forward 的**前 7 个窗口全在 2012 之前**
> —— 那几个窗口根本没有基准。metrics 会照常返回一个 `Bench` 结构，
> `Excess` 是 0。不存覆盖数的话，「没有基准」会被静默变成
> 「超额恰好为零」，而排序正是按超额来的。
> 实现里的处理是：`Covered == 0` 时**不设 `HasBenchmark`**，
> `Score()` 退回「总收益 ÷ 最大回撤」。

高原评分**不落盘**，查询时算 —— 它依赖阈值，而阈值会调。

## 8. 入口与分工

| | 谁 | 为什么 |
|---|---|---|
| 跑海选 | `cmd/sweep` CLI | 一次 8~13 分钟，不该塞进 HTTP 请求 |
| 看结果 | Web 新视图「海选」 | 读 Parquet，与其他视图同一形态 |
| 临时分析 | Python / DuckDB | 表是开放格式，不锁在引擎里 |

```bash
go run ./cmd/sweep -config ../configs/sweep/macd_coarse.json -workers 8
```

跑的过程要有**进度**（第几个窗口 / 第几组参数 / 预估剩余），
并且**可中断续跑** —— 13 分钟的任务被 Ctrl-C 打断后从头再来很难受。
续跑靠已写出的 Parquet 分片判断哪些 (param_id, window) 已完成。

Web 视图要展示的，按重要性：

1. **噪声基线**与「全网格散布 / 基线」的比值 —— 先回答「这次海选有没有意义」
2. 高原排名（区域中心参数、邻居数、OOS 中位数、IQR、正的比例）
3. 单个区域展开：18 个窗口的 OOS 分布（箱线图）
4. 任一行 → 复制配置去「回测」或「单步调试」复现

- 任取一行能用其 `input_fp` 复现出同样的 `output_fp`

## 10. 实现记录（2026-08-30）

第一至三刀已落地。三处**实现时才发现**的问题，都不是设计能推出来的：

### ① 预热段会把绩效算错，而且看不出来

窗口多裁一段预热前缀之后，OOS 那一跑的净值曲线包含了整段预热
（4 年数据里 3 年不交易、权益恒定）。后果不是「多几个点」：

- 年化系数按 970 步算 → **年化收益被摊薄 4 倍**
- 3/4 的收益序列恰好是 0 → **年化波动被压低、夏普被系统性抬高**

而这些数字看上去完全正常，不会有任何报错。
修法是绩效只算在实际交易区间上（`config.trimToTradeFrom`，
保留 `TradeFrom` 前一个点作为收益基准起点）。

### ② `steps` 与 `from_day..to_day` 必须同口径

第一版 `steps` 记的是**引擎步数**（970，含预热），
而 `from_day..to_day` 是绩效区间（1 年）。同一行里两个字段说着两件事。
改成都取绩效的口径。

### ③ 网格几何从结果反推，不从展开时带出来

分析层只拿得到 Parquet 里的参数 JSON。
`BuildGrid` 由参数组反推每一维的取值与坐标 ——
这样「跑」与「分析」完全解耦，跑完之后随时可以换阈值重新分析，
不必重跑 8,000 次回测。代价是**非数值维度无法参与高原判定**
（`base: initial|equity` 这种没有「±1 格」），实现里直接报错而不是猜。
