# 规则树 —— 在界面上拼出一个策略

> 2026-08-30。起因：「装配器应该还可以调控引擎所需的指标，然后引擎根据
> 指标值提供一个决策树的组装」。

---

## 1. 三棵树

| 树 | 管什么 |
|---|---|
| 是否买进 `buy` | 什么时候**算作一次机会** |
| 是否有效 `valid` | 这次机会**要不要真的下注** |
| 是否卖出 `sell` | 什么时候离场 |

```
buy ∧ valid   → 真实开仓
buy ∧ ¬valid  → 虚拟持仓：不动资金，但记成持有
sell          → 平仓（真实）/ 清掉虚拟标记
```

### 虚拟持仓是这套模型里最不显然的一件事

「买进为真但无效」时不下单，却把它记成持有 ——
于是**在它的卖出信号出现之前，不会再次触发买入**。

它解决的是一个真实的麻烦：像「MACD 在零轴上方」这类条件会**连续多根 bar
为真**，只用 buy 树的话每根 bar 都会尝试开仓。而真正想表达的往往是
「这一轮机会已经用掉了」。

换个说法：buy 树管**什么时候是机会**，valid 树管**这次要不要下注**。
两者分开之后，「不下注」不再等于「下一根 bar 再问一次」。

> 若 `valid` 为空，视为恒真 —— 行为与普通的两棵树策略一致。

## 2. 条件与表达式

节点要么是**逻辑组**（`and` / `or` / `not` + 子节点），要么是**条件**：

```json
{"left": {"kind":"ind","ind":"kdj","field":"J"},
 "cmp":  "lt",
 "right":{"kind":"value","value":80}}
```

左右侧三种：

| kind | 含义 |
|---|---|
| `bar` | 行情列：close / open / high / low / preclose / volume / amount |
| `ind` | 指标列：`ind` 是**用户起的实例名**，`field` 是该指标的输出字段 |
| `value` | 常数 |

比较符：`gt` `gte` `lt` `lte` `eq` `ne` `cross_above` `cross_below`。

### 可选列由启用了哪些指标决定

条件下拉里只会出现**指标表里声明过的**字段 ——
加了 KDJ 才有 `kdj.K` / `kdj.D` / `kdj.J`。
字段名来自 `/api/modules` 的指标目录，前端不维护。

新增的 `indicator.Catalog` 是「名字 → 构造器 + 参数规格 + 输出字段」的表。
输出字段单独存一份而不是问实例的 `Names()`，因为**界面要在用户还没添加
指标之前**就知道选了 KDJ 会多出哪几列。两者由
`TestCatalogFieldsMatchNames` 保证不分叉。

### 价格列一律是后复权价

与指标同基准。拿原始价去和均线比，除权日会凭空产生一次穿越 ——
那不是行情，是分红。为此给 `StepContext` 加了 `AdjBar`
（原来只有 `AdjClose`，而条件也能引用 open / high / low）。

## 3. 顺带挖出一个真 bug

用规则树复现 `macd_cross` 时对不上：+27.29% vs +11.06%。查下去发现两处。

### 3.1 我这边：穿越状态在持仓期间过期

第一版只在「未持仓时求 buy 树、持仓时求 sell 树」。
但穿越条件靠**上一步的差值符号**判定，那份状态必须像指标一样每步更新。
持仓期间不算 buy 树，它的穿越状态就此过期 —— 等卖掉之后再评估，
拿的是很久以前的 prev。

改成**三棵树每根 bar 都求值**，与是否持仓、是否在途无关；
求值完了才谈能不能下单。

### 3.2 原生 crossover.go：预热完成那一根有一次假金叉

```go
prev := c.prevAbove[id]   // 零值 false = 「在下方」
c.prevAbove[id] = above
return above && !prev, !above && prev
```

`prevAbove` 对**没见过的标的**返回 `false`。于是指标预热完成的那一根，
所有 DIF 已经在 DEA 之上的标的**同时**被判成金叉 ——
而那不是穿越，是状态检查。

实测在 285 只标的上，这一天会凭空多出一批买入信号，
而 `slots=10` 只能成交 10 笔，**成交哪 10 笔近乎任意**。
（这也是 v0.5 测到的巨大噪声的贡献之一。）

修法：加一个 `seen` 集合，第一次见到时两者都返回假。
快照也跟着改成存 1/−1 而不是「只存 true 的项」——
否则「见过且在下方」与「没见过」在快照里无法区分，
恢复后会重现那次假金叉，而 C6 的实盘每天从快照恢复。

### 3.3 修完之后：逐位一致

| | 输出指纹 | 总收益 |
|---|---|---|
| 规则树（MACD 金叉买 / 死叉卖） | `2bf137b307f9df43…` | +18.37% |
| 修正后的原生 `macd_cross` | `2bf137b307f9df43…` | +18.37% |

**逐位相同。** 这是对规则树最强的验证 ——
用户在界面上拼出来的东西，与手写的策略走的是同一条路径。

### 3.4 基线随之变化

| 配置 | 修正前 | 修正后 |
|---|---|---|
| `buy_and_hold` | +31.16% | +31.16%（不变，无穿越状态） |
| `ma_cross` | −36.99% | **−43.89%** |
| `macd_cross` | +11.06% | **+18.37%** |

这是**有意的行为变更**，不是重构走样。ROADMAP 里记录的基线指纹已更新。

## 4. 装配层的一处扩展

普通策略的参数是 `map[string]float64`（由 `ParamSpec` 描述），
而规则树的配置是三棵树加一张指标表 —— 那不是标量，塞不进 `Params`。

于是加了 `ConfigurableStrategy`：

```go
type ConfigurableStrategy interface {
    Configure(raw json.RawMessage) error
}
```

实现它的策略由装配层直接把整段 JSON 交过来自行解析，
**并跳过标量参数校验**（它没有 ParamSpec 可校验）。
校验改由 `Configure` 自己做，而且查得更细：引用了不存在的指标、
字段名写错、比较符不认识、两侧都是常数、`not` 有多个子节点 ——
全都在 `dryBuild` 阶段失败，跑之前就知道。

## 5. 已知边界

- **规则树不能进海选参数网格。** 网格扫的是标量维度，
  而树的形状不是一个可以 ±1 格的量。要扫的话应当把树里的**阈值**
  提成命名参数 —— 那是另一件事。
- 条件里没有「N 天前的值」。`close > close[-5]` 这类需要历史窗口，
  当前的 `Operand` 只表达「当前这一根」。要加的话是给 `Operand`
  补一个 `back` 字段，并让求值侧走 `History`。
- 没有跨标的的条件（如「大盘涨了才买」）。那需要在条件里引用**另一个标的**，
  是一个更大的口子。
