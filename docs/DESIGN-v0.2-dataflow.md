# v0.2 第一刀设计草案：市场数据流

> **状态：待评审**
> 最后更新：2026-08-29
> 依据：[ROADMAP.md](ROADMAP.md) 的 C1 / C4 / C5 / C6 / C9，[SCHEMA.md](SCHEMA.md)

本刀的产出是一个**能按事件时点推进、每步吐出当前可见数据、但不下单**的空引擎。
Market / Broker / Portfolio / Fee 不在本刀范围内。

之所以把数据流、时间模型与 `Step()` 骨架**捆在一起**做：
`DataGateway` 的接口形态取决于引擎怎么步进，先定死 Gateway 再改 `Step()`，
Gateway 必然重写；而 C4 明确「写成 for 循环后再改状态机等于重写」。

---

## 1. 时间模型 —— 多市场的统一基础

### 1.1 时钟是「事件时点序列」，不是「日期序列」

引擎的时钟是所有已加载标的的 `ts_close` **去重排序后的序列**。
每次 `Step()` 前进到下一个不同的 `ts_close`。

这一个决定同时解决了多市场的三个问题：

| 场景 | 自然落地方式 |
|---|---|
| A 股日线 | 每步 = 一个交易日的 15:00 CST |
| 加密 24×7 分钟线 | 每步 = 一分钟收盘 |
| 多市场同时回测 | 各市场的时点按真实 UTC 时间**交错**排列，无需特殊处理 |
| 某市场休市 | 该市场当步没有 bar，横截面里自然不出现 |

**引擎核心不需要知道「交易日历」这个概念** —— 日历是 ETL 的产物，
已经体现在 bar 表里；引擎只消费 bar 存在与否这个事实。
这正是 C9 要求的「接口中不得出现 `9:30-15:00` 这类常量」。

```go
type TimePoint struct {
    TsClose    int64 // UTC 毫秒 —— 该 bar 信息可得的时刻，时间游标唯一依据
    TradingDay int32 // YYYYMMDD —— 业务语义，用于展示与按日聚合
}
```

`ts_open` **不进内存**：引擎不需要它（C1 要求游标用 `ts_close`），
留在 Parquet 里供外部对齐与展示。

### 1.2 为什么不用交易日历驱动

若用日历驱动，多市场时就要处理「A 股休市但美股开市」的合并逻辑，
且加密货币根本没有日历。用 `ts_close` 的并集则完全无需分支。

## 2. 内存布局 —— 单标的与多标的的取舍

### 2.1 两种访问模式是冲突的

| 模式 | 谁用 | 需要的布局 |
|---|---|---|
| **单标的时序**：某标的最近 N 根 bar | 技术指标（滚动窗口）、单标的策略 | 标的连续 |
| **横截面**：某时点全部标的 | 选股策略、组合估值、风控 | 时点连续 |

同一份数据不可能对两者都连续。必须选一个做主序，另一个用索引补。

### 2.2 决定：标的主序 + 时点索引

**主序按标的**（与 SCHEMA.md 0.5 的 `(instrument_id, ts_close)` 排序一致，
Parquet 读进来就是这个顺序，零重排）：

```
列式数组（全局连续）：
  open[]  high[]  low[]  close[]  volume[]  amount[]  preclose[]
  tradingDay[]  tradeStatus[]  isST[]

标的偏移表：
  instrumentSpan[iid] = {start, length}   → 该标的的连续区间

时点索引：
  stepRows[stepIdx] = []int32             → 该时点有 bar 的行号
```

- 单标的时序：`instrumentSpan` 直接给出连续切片 → 指标滚动窗口是顺序访问，cache 友好
- 横截面：`stepRows[t]` 给出 gather 列表 → 一次间接寻址

**为什么主序选标的**：指标计算是热点。20 日均线在 5000 标的 × 5000 天上，
若布局不利会成为最大瓶颈；而横截面每步只访问一次，多一层间接寻址无关紧要。

`stepRows` 的额外内存：17.6M × 4 字节 ≈ **70 MB**，可接受。

### 2.3 列式而非行式

不用 `[]Bar` 结构体数组，理由是海选场景：
N 个 worker 共享同一份只读数据时，只读所需列能显著减少 cache miss。

**实测支持这个选择**（见 7.1）：只取收盘价 51.1 ns/根，
取完整 10 列的 Bar 则要 158.8 ns/根 —— 多列聚合占了 68% 的开销。
策略只用 close 时，列式布局省掉的正是这 68%。

### 2.5 ⚠️ 一条被实测推翻的推断

初版写的是「横截面每步只访问一次，**多一层间接寻址无关紧要**」。

**这句话错了，差距是两个数量级**：

```
单标的顺序扫描       1.0 ns/行
横截面只取收盘价    51.1 ns/根   ← 51 倍
横截面取完整 Bar   158.8 ns/根   ← 159 倍
```

原因是标的主序布局下，同一时点的行号在全局数组里是**散布的**，
每次访问都是一次 cache miss；取 10 列就是 10 次。

**但这不改变布局选择**，因为绝对量级仍可接受：
全量 1767 万根 bar 走一遍完整 Bar 是 2.8 秒、只取收盘价是 0.9 秒。
单次回测完全够用。

**真正需要警惕的是海选**：1000 组参数 × 2.8 秒 ≈ 47 分钟**仅数据访问**。
因此海选场景必须：

1. 策略只取所需列，不构造完整 `Bar`（省 68%）
2. 消除 `Universe`/`Bar` 路径上的 map 查找 —— `Advance` 已知标的下标，
   应直接返回下标而非 ID，让调用方跳过 `idIndex` 哈希
3. 海选通常只跑标的子集，横截面规模远小于全市场

### 2.4 内存预算

17.6M 行 × 各列宽度：

```
int64 × 7 (open/high/low/close/volume/amount/preclose)  = 986 MB
int32 × 1 (tradingDay)                                  =  70 MB
int8  × 2 (tradeStatus/isST)                            =  35 MB
stepRows 索引                                            =  70 MB
                                                    合计 ≈ 1.16 GB
```

两个可选优化（**均需实测后再定**）：

1. **按需加载列**：策略不用 `amount` / `preclose` 时不载入 → 可省约 280 MB
2. **内存内窄化**：A 股价格上限约 3000 元 × 1000 = 3e6，`int32` 足够；
   `volume` / `amount` 仍需 `int64`。窄化后价格列由 563 MB 降至 281 MB

> 窄化只在内存内进行，**不改 SCHEMA**：磁盘格式必须保持跨市场统一（加密需要 int64）。
> 窄化的宽度由 `instruments.price_scale` 与该市场的价格上限决定，属加载器的实现细节。

## 3. 未来函数防护 —— 修正 C1 的措辞

### 3.1 Go 做不到「编译期禁止越界访问」

ROADMAP C1 写的是「用类型系统在**编译期**禁止越界访问」。
严格讲，Go 的类型系统**无法对一个整数偏移做编译期约束** ——
`At(-1)` 一样能编译通过。这条措辞需要修正。

### 3.2 能做到的更强的事：让未来**不存在**

比运行时检查更强的是：**策略持有的视图里根本没有未来数据**。

```go
// History 是策略能拿到的唯一数据入口。
// 其内部切片的末尾就是当前 bar —— 未来不是「不可访问」，是**物理上不在里面**。
type History struct {
    col   *Columns // 全局列式数据（只读）
    start int32    // 该标的的起始行
    cur   int32    // 当前 bar 的行号（含）
}

// At(0) 是当前 bar，At(1) 是前一根，依此类推。
// 没有任何方法能取到 cur 之后的数据 —— 它不在 [start, cur] 区间内。
func (h History) At(back int) (Bar, bool)
func (h History) Len() int          // = cur - start + 1
func (h History) Close(back int) (int64, bool)
```

关键点：

- `History` 是**值类型**，每步由引擎更新 `cur` 后传入，**零分配**
- 底层切片**不外泄** —— 没有返回 `[]Bar` 或 `[]int64` 的方法
- `At(-1)` 返回 `false`，不 panic —— 这是调用方的 bug，但即便如此也拿不到未来
- 策略拿不到 `Columns` 指针，无法绕过

> 我建议把 C1 的措辞从「编译期禁止」改为
> **「未来数据不进入策略可见的视图」**——前者做不到，后者是更强的保证且能做到。

### 3.3 一个仍需人工把关的口子

指标与策略若自行缓存 `History` 值并跨步使用，`cur` 是拷贝时的值，
不会看到未来 —— 安全。但若缓存了 `*Columns`（需通过非导出字段，正常写法拿不到），
则可越界。**因此 `Columns` 必须在独立包内且字段非导出。**

## 4. 技术指标的步进计算

### 4.1 增量计算不只是为了快，更是 C1 的结构性保证

指标每步只 `Update(bar)` 一次、内部维护状态，**它连"看到未来"的能力都没有** ——
因为它从来没有拿到过完整序列。

性能差距也是决定性的。20 日均线，5000 标的 × 5000 天：

```
每步重算窗口   5000 × 5000 × 20 = 5.0 亿次
增量（环形缓冲） 5000 × 5000 × O(1) = 2500 万次
```

海选 1000 组参数时，这个差距直接决定可行性。

### 4.2 接口

```go
type Indicator interface {
    Update(b Bar)                    // 每步一次，O(1)
    Value() float64                  // 当前值
    Ready() bool                     // 预热是否完成（MA20 需 20 根）
    Snapshot() ([]byte, error)       // C6：实盘增量需要恢复状态
    Restore([]byte) error
}
```

- **每个标的一个实例**：5000 标的 × K 个指标，单实例状态很小（环形缓冲 + 累加器）
- **`Ready()` 必须由策略检查**：预热期内不得下单，否则前 N 步的信号是垃圾
- **`Snapshot`/`Restore` 是 C6 的前提**：实盘每天从快照恢复，而不是重算 20 年

### 4.3 一个必须记录的数值问题

滚动累加（`sum += new; sum -= old`）会累积浮点漂移。
同一配置从 2010 年起跑与从 2015 年起跑，2020 年的 MA 值会有微小差异。

这**不违反 C5**（配置里含起始日期，同配置结果仍逐笔一致），
但在 Walk-Forward 场景下，不同窗口的同一日指标值会不同 —— 属预期行为，需在文档中写明。

若要求绝对一致，则需定期重算窗口或用补偿求和（Kahan），代价是性能。
**建议先按朴素累加实现，把漂移量测出来再决定**。

### 4.4 指标值用 float64，不用定点

价格用定点是为了 C5（并发累加顺序不同导致结果不同）。
指标是**单标的顺序更新**，不存在并发累加，float64 的确定性足够，
且均线、RSI 这类量本身就是分数，用定点反而要处理除法精度。

## 5. 实盘数据路径

### 5.1 同一个 `Step()`，只换 Feed 与 Executor

```go
type DataFeed interface {
    // 推进到下一个事件时点，返回该时点更新的 bar
    Next() (TimePoint, []BarUpdate, error)
}
```

- `HistoricalFeed` —— 从内存列式数据按 `stepRows` 逐步吐出
- `LiveFeed` —— 从实时源取当日 bar

引擎核心对两者无感知，这是 C6 的落地方式。

### 5.2 「信号时点 → 可执行时点」必须由 Market 决定，不能硬编码 T+1 ⚠️

草案初版写的是「T 日收盘算出、T+1 执行」。**这个说法是错的**，
它把主板的规则当成了全市场的规则。

**A 股有盘后固定价格交易**：15:05–15:30，按**当日收盘价**成交，时间优先撮合。
但**仅适用于科创板与创业板，主板没有**
（申报时间：科创板 9:30–11:30 / 13:00–15:30，创业板 9:15–11:30 / 13:00–15:30）。

也就是说，**科创板与创业板的 T 日收盘信号可以在 T 日当天成交**。

更进一步，各市场的「信号到执行」间隔本就各不相同：

| 市场 / 板块 | T 日收盘信号的最早可执行时点 |
|---|---|
| A 股主板 | T+1（次日集合竞价或连续竞价） |
| A 股创业板 / 科创板 | **T 日盘后定价**（以 T 日收盘价），或 T+1 |
| 加密货币 24×7 | **零间隔** —— T 日「收盘」即 T+1「开盘」，是同一时刻 |
| 美股 | 盘后交易时段 |

**结论**：引擎不得内建任何「T+1」假设。`Market` 模块需要提供

```go
// 给定信号产生的时点，返回最早可执行的时点与执行价基准
NextExecutable(id InstrumentID, signalAt TimePoint) (ExecWindow, bool)

type ExecWindow struct {
    At        TimePoint
    PriceRef  PriceRef // 收盘价 / 次日开盘 / 次日任意价
}
```

这与 C9「接口中不得出现写死的 `T+1`」是同一条要求，
只是初版草案自己违反了它。

#### 盘后定价在回测中的两个建模缺口

若要建模盘后定价成交，日线数据支撑不足，必须诚实标注：

1. **无盘后时段的独立成交量** —— 日线的 `volume` 无法拆出盘后定价部分，
   因此「能否成交、能成交多少」缺乏依据。时间优先撮合需要对手盘，不保证成交
2. **交收仍是 T+1** —— 盘后定价买入的股票，T+1 才能卖出

> ⚠️ **待确认**：日线 `volume` 是否已包含盘后固定价格交易的成交量。
> 这决定成交量约束该怎么算，需在 v0.2 实现 Broker 前查证。

### 5.3 盘中不完整 bar 的处理

盘中那根 bar 收盘价未定。若用盘中最新价冒充收盘价去决策，
回测与实盘的语义就不一致 —— 违反 C6。

因此**正式信号只在 bar 收盘后产生**。盘中「假设现在收盘会怎么做」的预演，
必须在 API 与 UI 上明确标记为预演，不与正式信号混用。

真正的盘中决策需要分钟线，属远期。

### 5.4 增量恢复

```
昨日快照（指标状态 + Portfolio + 时间游标）
    ↓ 载入
喂入今日 bar
    ↓ Step() 一次
今日动作
```

没有快照就要每天重放 20 年数据。因此**快照能力必须在本刀就设计进去**，
哪怕 v0.2 只实现指标状态部分（Portfolio 在下一刀）。

## 6. 接口草案汇总

```go
// ---- 引擎核心（C4：状态机，不是 for 循环）----
type Engine interface {
    Step() (StepResult, error)   // 前进一个事件时点
    Done() bool
    Snapshot() ([]byte, error)
    Restore([]byte) error
}

type StepResult struct {
    Time    TimePoint
    Updated []InstrumentID       // 本步有新 bar 的标的
}

// ---- 策略可见的数据入口 ----
type StepContext interface {
    Time() TimePoint
    Universe() []InstrumentID            // 本时点有 bar 的标的
    History(id InstrumentID) History      // 单标的历史视图（未来物理不在其中）
    Bar(id InstrumentID) (Bar, bool)      // 当前 bar
    Indicator(id InstrumentID, key string) Indicator
}

// ---- 复权（C2：存原始价 + 因子，按需动态复权）----
type Adjuster interface {
    // 把原始价换算为指定复权方式下的价格
    Adjust(id InstrumentID, day int32, rawPrice int64) int64
}
```

### 6.1 复权在四条路径上的用法不同 ⚠️

「回测用后复权还是前复权」这个问题的前提就不对 —— **不同用途用不同的价**：

| 路径 | 用哪种价 | 为什么 |
|---|---|---|
| **指标计算**（MA / RSI…） | **后复权** | 序列必须连续，否则除权日会产生假信号 |
| **撮合成交** | **原始价** | 成交发生在真实价位；涨跌停基于 `preclose`，同属原始价体系 |
| **账户市值 / 盈亏** | **原始价** | 持仓按真实市价计值；分红送股经 `corporate_action` 入账（C2） |
| **前端展示** | 可选**前复权** | 用户看图的习惯；不参与任何决策 |

初版草案写的「策略拿到的价格已按配置复权」是含混的 ——
策略同时需要后复权价（算指标）与原始价（判涨跌停、下单），两者不能二选一。

```go
type Adjuster interface {
    Adjust(id InstrumentID, day int32, rawPrice int64, mode AdjMode) int64
}

type AdjMode int8
const (
    AdjNone AdjMode = iota // 原始价：撮合、账户、涨跌停
    AdjHFQ                 // 后复权：指标
    AdjQFQ                 // 前复权：**仅展示路径可用**
)
```

**`AdjQFQ` 必须在类型或调用路径上与策略隔离** —— 它锚定末日，
每次新除权都改写历史，在决策中使用即构成未来函数（C1）且不可复现（C5）。
建议做法：策略侧的 `History` 根本不接受 `AdjQFQ` 参数，
前复权只存在于展示层的独立接口上。

### 6.2 视图可刷新

Web 端切换复权方式、调整参数时，**不应重新加载原始数据**。

原始列式数据是只读的、全局共享的；`Adjuster` 与 `History` 都是**轻量视图**，
切换 `AdjMode` 只是换一个换算函数。这也是 2.2 节「标的主序 + 时点索引」
布局的附带收益：视图切换零拷贝。

## 7. 实测结果

本刀的价值有一半在于**把猜测变成数字**。以下由 `engine/cmd/loadbench` 实测，
环境：Windows 11 / go1.26.1 / 数据 17,670,265 行。

### 7.1 已测（4 项）

| # | 项 | 结果 |
|---|---|---|
| 1 | 全量加载耗时 | **34.6 秒**（统计 14.0s + 填充 19.7s + 索引 0.8s） |
| 2 | 实际内存占用 | **1,253.6 MB**（估算 1,247.2 MB，**估得准**）；74.0 字节/行；内存/磁盘 = 3.90x |
| 3 | 列式 vs 行式 | 只取 1 列 51.1 ns/根 vs 取 10 列 158.8 ns/根 → **列式省 68%** |
| 6 | 增量指标 vs 每步重算 | 每步重算 MA20 比顺序扫描慢 **26.8x**（4.1 节估的是 20x） |

附带测得：

- 步进（仅推进游标）：**10,470 步/秒**，28 ns/次 bar 更新
- 单标的顺序扫描：**1.0 ns/行**
- 覆盖 7,175 只标的 / 5,260 个事件时点

> 加载 34.6 秒对单步调试的启动体验偏慢，但对海选无所谓（一次加载多次复用）。
> 若要优化，第一遍统计占 14 秒，可考虑把每标的行数写进 `_manifest.json`
> 由 ETL 侧产出，直接省掉这一遍。

> 28 ns/更新中含 `instrumentIndexOfRow` 的二分（约 13 次比较）。
> 这是「不为每行额外存 int32 标的下标」换来的 —— 省 70 MB，代价是这 28 ns。
> 若后续证明步进是瓶颈，可用空间换时间。

### 7.2 待测（4 项）

| # | 待测 | 为什么必须测 |
|---|---|---|
| 4 | 价格列窄化到 int32 的收益 | 省 281 MB 是否值得引入市场相关的分支 |
| 5 | 按需加载列的收益 | 同上 |
| 7 | 滚动累加的浮点漂移量 | 决定是否需要 Kahan 求和（4.3 节） |
| 8 | Go 复权结果与 Python 的一致性 | **C5 的第一道关**，不一致则可复现性从第一步就破 |

## 8. 验收标准

| 项 | 标准 |
|---|---|
| 正确性 | 按事件时点推进，任意时点只能取到 `≤ 当前 ts_close` 的数据 |
| 未来函数 | 策略视图内**物理上不含**未来数据（3.2 节），且 `Columns` 字段非导出 |
| 状态机 | 核心是 `Step()`，无内部 for 循环；可在任意步暂停并检视（C4） |
| 复权一致性 | Go 侧复权价与 Python 侧**逐位一致**（C5 第一道关） |
| 多标的 | 单标的时序与横截面两种访问都有实现且有基准数据 |
| 指标 | 增量计算，`Ready()` 语义正确，`Snapshot`/`Restore` 可往返 |
| 快照 | 引擎状态可序列化并恢复，恢复后继续步进结果一致 |
| 性能 | 第 7 节八项均有实测数字并记录在案 |

## 9. 评审决议（2026-08-29）

| # | 问题 | 结论 |
|---|---|---|
| 1 | C1 措辞修正 | ✅ 接受。全量数据可一次性载入内存，但**暴露给引擎/前端/外部的视图不含未来数据**；且切换复权等配置时视图可刷新（见 6.2） |
| 2 | 指标状态归属 | ✅ **引擎持有**，便于复用与快照，并支撑远期「用户自由配置所需指标」 |
| 3 | 浮点漂移 | ✅ 先按朴素累加实现，测出漂移量再决定是否上 Kahan |
| 4 | 盘中预演 | ✅ v0.2 先做**可逐步提供的数据视图**（单标的与多标的均需），预演本身延后 |
| 5 | 是否含复权 | ✅ 含。并厘清四条路径各用哪种价（见 6.1）—— 前复权仅限展示 |

**另一项由评审推翻的初版设计**：初版把「T+1 执行」当作全市场规则，
实为主板规则；科创板与创业板有盘后固定价格交易，T 日信号可 T 日成交，
加密货币则完全无间隔。已改为由 `Market` 提供 `NextExecutable`（见 5.2）。

## 10. 遗留的开放问题

1. **日线 `volume` 是否含盘后固定价格交易的成交量**（5.2）——
   决定成交量约束怎么算，需在实现 Broker 前查证。

2. **`NextExecutable` 的执行价基准如何表达**（5.2）——
   科创板/创业板的盘后定价以当日收盘价成交，主板 T+1 则可能是开盘价或区间内任意价，
   `PriceRef` 的取值集合需要在 Broker 那一刀定死。

3. **盘后定价的成交概率如何建模**（5.2）——
   时间优先撮合需要对手盘，日线数据无从判断。是一律假设成交，还是按当日成交量的
   某个比例设上限？倾向后者，但需要一个有依据的比例。
