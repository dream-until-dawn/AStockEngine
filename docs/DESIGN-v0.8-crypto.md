# v0.8 加密永续：逐仓、双向、按市场计价

> 目标：让加密市场真的能跑回测，且**跑出来的数字是对的**。
>
> v0.3.3 接了加密的数据通道，但交易规则层是空的 —— `checkMarketRules`
> 直接拒绝，宁可不跑也不给一份「看着正常的假结果」。这一版把规则层补上。

约束来自需求方的三句话：**加密固定逐仓 + 双向开仓持仓**、
**计价货币随市场不同**（加密 USDT 默认 1,000，A 股默认 20,000 元）、
**加密基准取 BTC 永续**。

---

## 1. 这一版真正的难点不是「加个市场」

难点是：**这个市场的每一处差异，出错时都不报错。**

A 股与加密的差异不在于「有没有涨跌停」这类能被 `if` 挡住的开关，
而在于一批**量纲**：价格标度 1e3 vs 1e8、数量标度 1 vs 1e8、
合约乘数 1 vs 0.01、年化 243 vs 365、计价单位 元 vs USDT。
量纲错了不会 panic，只会给出一个数量级不对但格式完全正常的数字。

这一版修掉的每一个 bug 都是这个形状。逐个记下来，因为它们不是
「设计能推出来」的，而是**测出来的**。

## 2. 金额与数量：128 位与逐标的 scale

### 2.1 溢出是静默的

`price_fp × qty_fp` 在 BTC 上是 `9.87e11 × 2.53e8 ≈ 2.5e20`，
超过 int64 上限 9.22e18。乘法不报错，只是回绕成一个负数或小数。

`NotionalCents` / `QtyForCents` / `MulDiv` 一律走 `math/bits.Mul64` +
`bits.Div64` 的 128 位中间量。

### 2.2 名义额的换算比不能靠浮点算

`NotionalRatio()` 返回一对整数 `(num, den)`，由合约乘数、价格标度、
数量标度约分而来：A 股 → `1/10`（与旧代码 `price*qty/10` 逐位相同，
由 `TestNotionalMatchesAShareLegacy` 钉住），BTC → `1/1e16`。

合约乘数从 `attrs.ct_val` 读的是字符串 `"0.01"`，**按字符串转定点**，
不经过 float64 —— `0.01 × 1e8` 走浮点得到的是 `999999.9999999999`。

### 2.3 被这一类坑到的三处

| 处 | 症状 | 原因 |
|---|---|---|
| `sizer.go` / `risk.go` | 168 条信号 → 0 笔成交 | `budgetCents * 10 / bar.Close` 是 A 股口径，算出的张数被 `NormalizeQty` 判成 0 |
| `broker.go` 成交量上限 | 114 笔「超出成交量占比上限」的假拒单 | `b.Volume * VolumeCapPPM` = 1.25e22 回绕 |
| 报告 | `未平仓 2 只 / 1352000000 股` | 定点数量直接印，且跨标的相加 —— 不同 scale 的数量相加本身没有意义 |

第三处的修法不是「除以 scale」而是**换一个量**：报告改印
`未平仓 2 只，开仓金额 925.39 USDT`。金额跨标的可加，数量不可加。

## 3. 逐仓与双向：`MarginLedger`

`Ledger` 接口在 v0.3.2 就按保证金账户设计好了（`Exposure` 分多空、
`Mark()` 返回 `[]Liquidation`），当时现货实现里它们恒为空。
这一版填上第二个实现，接口一行没改 —— 这是那次抽象的回报。

### 3.1 逐仓 = 亏损以该仓位的保证金为限

强平时 **保证金全损，余额不动**。测试
`TestMarginIsolatedLiquidationCapsLoss` 钉的就是这一条：
5 倍杠杆下名义额 100.00、保证金 20.00，价格跌 30% 时浮亏 30.00 ——
账户损失必须停在 20.00，可用余额一分不动。

`BuyingPowerCents` 因此是 **余额 × 杠杆**，不是权益 × 杠杆：
已开仓位的浮盈属于那个仓位，拿去开新仓等于把逐仓变回全仓。

### 3.2 双向 = 每个标的两个槽

`long` / `short` 两个 map，不是一个带正负号的净头寸。
「买 100 张」在已有 100 张空单时，单向下是平仓、双向下是开多 ——
意图完全不同，由 `Order.Reduce` 区分。

## 4. 一张表，四个地方 —— `trading.LegOf`

开平方向的映射表：

```
双向：买+开=开多   买+平=平空   卖+开=开空   卖+平=平多
单向：买恒为开多，卖恒为平多（reduce 不看）
```

这张表**原先在四个地方各写了一遍**，而且是逐个被发现的 ——
每修好一个，下一个才暴露出来：

| # | 地方 | 写错的表现 | 怎么发现的 |
|---|---|---|---|
| 1 | `MarginLedger.posFor` | 记错槽位 | 写实现时就想到了 |
| 2 | `metrics` 轮次配对 | 空头轮的盈亏符号相反；平空被当成开多，永远不平 | 报告里 `平均持有 190.8 天` × 314 轮 = 59,911 仓位·日，而 4 槽 × 2432 天只有 9,728 |
| 3 | `sizer` 建仓方向 | **开空变成开多** | 数了一下成交的开平分布：`买开=170 买平=0 卖开=0 卖平=166` —— 一笔空单都没有 |
| 4 | `Composite` union 去重 | **开空信号被平多信号顶掉** | 修完 3 之后再数：`卖开=2`。还是几乎没有 |

第 4 处最隐蔽：`sigKey` 是 `(标的, 买卖方向)`，注释里写着
「真正互斥的是买与卖」—— 在单向市场里完全正确。但双向下
「卖」有两个意思，一多一空两棵镜像的树在 MACD 下穿那一根上
同时发出「平多（卖）」和「开空（卖）」，后者被前者去重掉了。

**四处的共同点：全都不报错。** 所以把表抽成 `trading.LegOf` 一个函数，
四处共用。写在一个地方，改也只用改一个地方。

> 单向市场的口径**一个字没变**：`LegOf(side, reduce, false)` 忽略 `reduce`，
> `sigKey` 退化成 `(标的, 方向)`。`TestUnionSpotStillDedupesBySide` 守这一点。

### 4.1 仓位槽也要分方向

`occupancy` 原先按标的去重，于是「持有 BTC 多头」会挡住「开 BTC 空头」——
那正是双向要做的事。改成 `slotKey{标的, 方向}`，单向下 `short` 恒为 false，
键退化回标的本身。

### 4.2 修完之后

| | 修前 | 修后 |
|---|---|---|
| 开平分布 | 买开 168 / 买平 167 / **卖开 0** / 卖平 166 | 买开 168 / 买平 167 / **卖开 168** / 卖平 166 |
| 信号 | 336 | 669 |
| 轮次 / 平均持有 | 314 轮 / 190.8 天 | 405 轮 / 34.5 天 |
| 总收益 | +146.07% | +129.64% |

收益变低是对的：在一个基准涨了 982% 的市场里补上空头腿，本来就要亏钱。

> **一个我先判错的地方**：最初看到「336 笔成交配出 314 轮」，
> 我说轮次上限应是 168、这证明配对坏了。**这个推理是错的** ——
> 一笔平仓可以吃掉 FIFO 队列里的好几层，每层算一轮，
> 所以轮次多于平仓笔数完全正常。真正的证据是那个
> 190.8 天 × 314 轮的仓位·日数超了槽位上限 6 倍。
> 结论没变，但当时给出的理由不成立。

## 5. 计价与展示：单位不是标签

`Market.Units() (money, qty string)` 进了接口，而不是在报告里按市场名查表。

查表漏一个市场只会安静地印出「元」，而加密账户的余额不是元。
放进接口，新市场不实现就编译不过。

同样的理由，服务端把 `market{impl, money, qty, hedge, annualDays}`
和**每一行自己的 `priceScale` / `qtyScale`** 一起下发，前端照抄，
不按市场名自己判断。

### 5.1 强平消息也是展示

原先印 `强平 7201：buy 253000000 股 @ 613510000000` —— 三个数没一个能读。
改成印**名义额与损失的保证金**：这两个量不需要 scale 就有意义。

## 6. 每个市场自己的默认值

| | A 股 | 加密 |
|---|---|---|
| 初始资金 | 20,000 元 | 1,000 USDT |
| 账本 | `spot` | `margin`（逐仓双向） |
| 市场规则 | `ashare` | `crypto` |
| 基准 | 无（由配置指定 ETF） | `BTC-USDT-SWAP` |
| 年化系数 | 由日历数出（约 242.54） | 365 |

加密的初始资金若沿用 20,000，报告会印「初始 20000.00 USDT」——

`market_defaults_test.go` 把四条都钉住，外加一条
「写了就以写的为准」——默认值最坏的失败方式不是给错，是盖掉用户写的。

## 8. 风控：熔断的冷静期与「策略已死」

### 8.1 冷静期不是「等回撤收窄」

`drawdown_halt` 现在有三种形态：

| cooldown | flatten | 行为 |
|---|---|---|
| 0 | 关 | 纯拦截。只要还在回撤线下就禁新仓，回上去自动恢复（**历史行为，默认**） |
| N | 关 | 触发后固定停 N 根 bar，期间即便权益回来也不放行 |
| N | 开 | 触发时先清空持仓，再停 N 根 |

不设冷静期时，权益只要反弹一点越过阈值就立刻放行 —— 而那一点反弹
常常是下跌中继。冷静期表达的是另一个意思：**不是「跌够了没有」，
而是「先别动，让它走一段」**。

倒计时挂在 `OnStep`（每步都调）而不是 `Check`（有订单才调）：
挂在后者的话，没有订单的那些步不计数，「停 5 根」会变成
「停 5 次下单尝试」，而后者可能横跨几个月。

### 8.2 一个我加进去又测出来的陷阱：冷静期永远醒不过来

第一版实现里，冷静期结束后仍按**引擎的历史峰值**算回撤。
实测直接暴露了问题：

```
年      成交    拒单
2020     70       0
2021      0      40      ← 触发
2022      0      56
2023      0      57      ← 之后 5 年一笔没做
...
```

原因链条很短，但每一环都不报错：勾了清仓 → 账户全是现金 →
**权益不再变动** → 而历史峰值停在熔断之前 → 回撤永远回不到阈值以内 →
冷静期一到就立刻再次触发。从此再也不交易，而报告上只是一条平直的净值线。

修法：**冷静期结束时把参考峰值重设为当下的权益**，之后它跟着权益往上走。
「冷静期」本来的意思就是「停一段时间，然后重新开始」，
重新开始自然要从当下重新计量。不设冷静期（=0）时仍用引擎峰值，
行为一个字不变。

修完之后同一份配置：

```
年      成交    拒单
2020     70       0
2021     93       5
2022     98       6
2023    116       0      ← 触发 11 次，每次都醒得过来
2024     96       0
2025    120       0
2026     48       0
```

### 8.3 「平掉全部仓位」为什么要显式勾选

熔断一旦自己发卖单，就等于在策略之外新增了一条交易逻辑，
回测结果不再能干净地归因到策略本身 —— 亏损是策略的还是熔断的，分不出来。
**所以默认关闭**。打开之后它仍然是可归因的：平仓信号带
`tag=drawdown_halt`，报告里能按 tag 把这批成交拆出来。

双向市场下多空两条腿都要平，且方向相反 —— 只发卖出的话，
空头仓位会原封不动地留着。

### 8.4 `min_capital`：一个已经死掉的策略会显示成低波动策略

真正的失败不是「权益低」（那是回撤），而是**手里空了、钱也不够再开一手**：
从这一刻起后面每根 bar 都不可能再有成交，净值走成一条直线。

那条直线在报告里非常危险：最大回撤定格在失败那天、
年化波动被后面几年的零波动摊薄、**夏普反而变好看**。

两种判据：

- `floor > 0` —— 显式下限，权益低于它即判失败（用户点名要的「可选设定」）
- `floor = 0` —— 自动：这一步连一张最小申报单位的仓都开不起
  （BTC 一张 0.01 个、A 股一手 100 股，各不相同，所以按标的算）

判定必须同时挂在 `Check` 与 `OnStep` 上：破产之后 Sizer 算出的数量为 0，
**根本不会产生订单**，`Check` 也就永远不会被调用 ——
而「再也下不出单」恰恰是要检测的那件事。

判定后不撤销：无持仓、无成交的账户不会自己把钱变回来，
允许撤销只会让「失败」随权益浮动反复横跳。
命令行报告在绩效区块**之前**印出这一条，因为底下每个指标都会被它改变含义。

### 8.5 风控链的快照

熔断的冷静期是跨步状态，从前风控链根本不进快照。
补上 `StatefulRisk` 与 `RiskChain.SnapshotState/RestoreState`，
引擎快照多一个 `risks` 字段 —— 不存的话，从快照恢复的那一步
冷静期归零，**熔断静默解除**。

## 9. 杠杆：账户级可选，不是标的属性

期货每个合约有各自固定的保证金率，交易者选不了；
加密交易所让你在开仓时任选倍数，所以它是**配置项**而不是标的属性。

`portfolio.leverage` 取值 1–100（主流交易所 BTC/ETH 永续对普通用户的
常见上限；更高的档位要么限币种、要么限仓位规模，回测里假装有它没有意义）。

两条校验，都在跑之前：

- **维持保证金率不得高于开仓保证金率**。`1_000_000 / leverage` 是开仓
  保证金率，维持率不低于它意味着仓位一开出来就该被强平 ——
  那不是「风控严」，是参数写错了。
- **现货账本上不许设杠杆**。静默忽略的话，用户以为在跑 5 倍杠杆，
  拿到的是 1 倍的结果，而报告里看不出任何异常。

## 10. 持仓模式：仅做多 / 仅做空 / 双向

引擎侧**没有**「双向模式」这个开关。三种模式其实是配置的三种形态：

	long  —— 一棵 direction=long 的规则树
	short —— 一棵 direction=short 的规则树
	both  —— composite/union 组两棵树，一多一空

一棵树表达一个意图；硬塞进一棵只会让「这个条件是给多头还是空头的」
变成日常问题。装配器上的选单只是把这三种形态包装成一次点击，
切到双向时缺的那一边**原样复制**过去 —— 不自动取反：
取反是猜测，而猜错的条件照样跑得出结果，只是那结果不是你想要的。

「仅做空」「双向」只在支持做空的市场出现。**但界面藏起来只是方便，
不是保证** —— `Strategy` 多了一个可选接口 `ShortSeller`，
装配时问一句「你要开空吗」，要而市场不支持就直接报错。
不拦的话后果是静默失效：开空信号会被 Sizer 当成减仓，
手上没有多头可减，订单被丢掉 —— 一笔成交都不会有，
报告上却看不出任何异常。

## 11. OKX 的费率与交易限制（核对）

需求方给的数字与配置逐项对上了：

| | 需求方 | 系统里 |
|---|---|---|
| taker | 0.0005 | `rate_ppm: 500` ✓ |
| maker | 0.0002 | 注释里写明，改成 200 即可 ✓ |
| min_trade_contracts | 0.01 | `min_order_qty = 1e6 / 1e8 = 0.01 张` ✓ |
| min_trade_amount（lotSz） | 0.01 | `qty_step = 1e6 / 1e8 = 0.01 张` ✓ |
| granularity（tickSz） | 0.1 | 新增 `Instrument.PriceTick`，从 `attrs.tick_sz` 解析 |

**一律按吃单算**：日线只有一根 OHLC，判断不出成交是吃单还是挂单。
不做混合估计 —— 混合比例是拍脑袋出来的，而拍出来的数字会一路带进最终收益。
取吃单是明确地偏保守的一侧。

tick 在当前架构下**不影响成交价**：滑点记在 `SlippageCents` 里而不是
推动价格，`Fill.Price` 始终是行情里真实存在的 OHLC 值，天然落在 tick 上。
它的用途是限价单 —— 顺手修掉了撮合器拒单消息里写死的 `/1000`
（A 股价格标度），那在 BTC 上会印出一个大 10 万倍的数字。

## 12. 逐轮交易：这一轮是什么、又是怎么结束的

从前逐轮表里每一行长得一模一样。看不出三件事，而这三件事都不报错：

### 12.1 被强平的仓位永远「未平仓」

**强平不走撮合器** —— 账本自己动手平的仓，一笔成交都不产生。
于是逐轮配对里那个仓位永远配不上平仓，一直挂在「未平仓」里。

实测：336 笔开仓对 333 笔平仓，差的 3 笔中有 1 笔就是被强平的，
而报告只说「未平仓 2 只」。

修法：引擎把每次强平**补成一笔成交记录**（`Tag=liquidation`），
不调 `ApplyFill` —— 账在 `Mark()` 里已经记过了，再记一次就是重复扣。
这里只补「成交记录」这一面。

强平在事实上就是一笔交易：交易所按市价替你平了仓。
它该计入成交额、该产生一轮完整的盈亏、该在逐轮里标出来。
补出来的成交**进指纹** —— 强平改变了持仓，是结果的一部分。

> 因此**加密的输出指纹变了**（A 股不受影响：现货账本没有强平，
> 三个基线指纹逐位不变）。

### 12.2 离场原因

`Fill.Tag` 一直存在（止损/止盈/移动止损/熔断各自都设了），
但配对时被丢掉了。现在 `RoundTrip` 带 `OpenTag` / `CloseTag`，
报告与前端按它分组：

```
离场原因      熔断清仓 6    强平 1    卖出信号 313
```

认不出来的 tag **原样显示**，不归到「其他」—— 策略可以自定 tag
（A 股的 `macd_death` / `ma_death` 就是这样），混成一堆就等于把归因扔了。

### 12.3 虚拟持仓根本不在表里

虚拟持仓不产生成交，而逐轮表是从成交配出来的 —— 所以它们完全不存在。

但**「有效性」这棵树的全部价值，就在于它过滤掉的机会后来怎么样了**。
不把它们报出来，就没有任何办法判断这个过滤到底对不对。

`RuleTree` 现在记下每一轮虚拟持仓（开仓日 + 开仓价 → 平仓日 + 平仓价），
经 `VirtualReporter` 接口一路报到前端，与真实轮次并排显示、可筛选。

**只有收益率，没有金额。** 虚拟持仓从未占用资金，也就没经过 Sizer 定量 ——
硬给它安一个「本该赚多少钱」，那个金额是编出来的。
收益率是这笔决策唯一真实可算的东西。价格取**后复权收盘价**，
与条件求值同基准（拿原始价算，除权日会凭空多出一段涨跌）。

实测（`crypto_valid.json`，MACD 金叉买 + RSI<70 才算数）：

| | 轮次 | 平均收益率 | 正收益 |
|---|---|---|---|
| 实仓 | 152 | **+3.87%** | 59 |
| 被过滤（虚拟） | 13 | **−1.78%** | 3 |

这就是那棵有效性树该不该留的**证据**，而从前它一个数字都不显示。

> 虚拟持仓的开仓日与开仓价也进快照。只存标的 ID 的话，
> 从快照恢复后那笔虚拟持仓平掉时凑不出开仓端，整轮记录就丢了。
